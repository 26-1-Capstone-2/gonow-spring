# 대중교통 계산엔진 조사 — ODsay vs TMAP vs 카카오

GoNow의 출발 알람 계산 엔진을 ODsay에서 다른 provider로 교체(또는 병행)할 수 있는지 조사한 결과 정리. 결론부터 말하면 **ODsay를 대체할 수 없다** — `target_time` 기반 역산(데드라인 모드) · 막차 탐색(막차 모드)을 지원하는 provider가 ODsay뿐이기 때문. TMAP·카카오는 딥링크 등 다른 용도로는 여전히 유효하다.

## 왜 이 조사를 했는가

GoNow의 출발 알람 핵심 로직(`CLAUDE.md` "출발 알람 시각 계산 정책" 참고)은 두 가지를 요구한다:
- **데드라인 모드**: 사용자가 지정한 도착 시각(`target_time`)에서 시간표 기준으로 역산해 출발 시각을 계산
- **막차 모드**: `target_time` 없이 시작해서, 23:00~01:00 창에서 막차 시각 자체를 탐색(이진 탐색)한 뒤 그 시각이 `target_time` 역할을 함

이걸 만족하려면 provider가 "특정 시각 기준 시간표 계산"을 실제로 지원해야 한다. 이 한 가지 요구사항이 아래 조사 전체를 관통하는 판단 기준이다.

## 결론 요약

| Provider | target_time 기반 계산 | 수도권 경로 품질 | 딥링크 | 판정 |
|---|---|---|---|---|
| **ODsay** | O (`SearchDate`/`SearchTime` 파라미터, 실제 시간표 기반) | 양호 (아래 실측 참고) | 없음(자체 UI 필요) | **GoNow 계산 엔진으로 유지** |
| TMAP | X (아래 실측으로 반증됨) | 양호, 일부 구간 ODsay보다 나음 | 있음(미검토) | 계산 엔진 후보 탈락 |
| 카카오(신규, 2026-07-21 출시) | X (파라미터 자체 없음) | 양호, ODsay와 비슷 | O (`landingURL`, 검증 완료) | 계산 엔진 후보 탈락, **딥링크 용도로는 유효**(`reference/kakao-map-deeplink-spec.md` 참고) |

## 1. TMAP 대중교통 API — `searchDttm` 실측 결과

TMAP 공식 문서는 `searchDttm`(형식 `yyyymmddhhmi`)을 "타임머신 기능... 사용자가 설정한 시각에 이동수단의 운행여부를 안내"라고 설명한다. 진짜 시간표 재계산인지 실측으로 확인했다.

- 강남역→정자역, `searchDttm` 없이: 신분당선 직통 25.75분
- 같은 구간, `searchDttm=202608090100`(신분당선 막차 지난 새벽 1시): **totalTime 1545초로 동일**, 응답에 `service: 0`(운행종료) 플래그만 추가됨
- 즉 경로 자체는 재탐색되지 않고, 미리 계산된 경로에 "이 시각엔 운행 안 함" 표시만 얹는 방식

**결론**: TMAP은 시각 기반 진짜 경로 재계산을 하지 못한다. 데드라인 모드도, 막차 모드(막차 시각 자체를 탐색해야 함)도 구현 불가능 — 계산 엔진 후보에서 완전히 배제.

(참고: 정방향 탐색으로 우회하는 방안도 검토했으나, 애초에 TMAP 응답이 시각에 따라 달라지지 않으므로 반복 탐색 자체가 무의미함 — 우회 불가.)

경로 품질 자체는 나쁘지 않다. 서울역↔안성(66.6km) 구간에서는 오히려 ODsay가 놓친 고속버스 후보를 TMAP이 찾아낸 사례도 있었다(TMAP 106.5~148분 vs ODsay 167분). 다만 계산 엔진으로 못 쓰는 이상 이 장점은 GoNow에 직접 활용할 수 없다.

## 2. 카카오 대중교통 API (`dapi.kakao.com/v2/routing/publictraffic`, 2026-07-21 출시)

- `target_time` 또는 그에 준하는 시각 지정 파라미터가 **아예 없음** — TMAP처럼 무의미한 흉내조차 못 냄
- `landingURL` 필드는 카카오맵 앱 딥링크로 정상 동작 확인됨 → **딥링크 용도로는 채택 가치 있음**
- `WALKING` 스텝은 환승 구간에만 나오고 첫/막 도보(출발지→승차, 하차→목적지)는 응답에 없음 — 버그가 아니라 "대중교통 수단의 이용 경로 안내가 목적"이라는 카카오 공식 설계
- 70km 초과 도시간 구간은 `NO_RESULTS`
- 수도권 내 경로 품질은 ODsay와 거의 동일 수준(서울역↔인천공항 61분 등)

**결론**: 계산 엔진으로는 탈락(파라미터 없음), 그러나 딥링크 트랙에서는 독립적으로 유효 — `planning/feature-ideas.md`·`reference/kakao-map-deeplink-spec.md` 쪽 논의와 연결됨.

## 3. ODsay — 프로덕션 코드(`gonow-flask/.../gps_api/core/transit_route.py`)에서 확인된 사실

- `INTERCITY_DISTANCE_THRESHOLD_M = 70_000`(70km): 출발지-목적지 직선거리(haversine)가 이 값을 넘으면 `SearchType=1`(도시간), 아니면 `SearchType=0`(도시내)로 **이미 자동 분기하는 코드가 구현돼 있음**
- `PRIORITY_RANK_MAP`: ODsay의 `OPT` 파라미터에는 min-transfer/min-walk 개념이 없어서, GoNow가 응답을 받은 뒤 자체적으로 재정렬하는 로직
- `find_last_train_departure()`: 23:00~01:00 창에서 이진 탐색으로 막차 시각을 찾는 로직(막차 모드의 핵심)
- `walk_fallback()`: ODsay `-98` 에러(출발-목적지 700m 이내일 때) 도보 폴백 처리

**중요한 경위**: 예전에 "강남역→정자역에서 SearchType=1을 쓰면 동서울종합터미널→가천대정류소 고속버스로 엉뚱하게 30분 응답"이라는 버그성 결과를 관찰한 적이 있었다. 이건 SearchType=1을 **의도적으로 강제한 진단용 테스트**의 인공물이었고, 실제 프로덕션 코드는 16km인 이 구간에 자동으로 SearchType=0을 쓰므로 이 버그를 겪지 않는다 — 아래 4번 실측으로 최종 확인됨.

## 4. ODsay `SearchType=0` 수도권 커버리지 실측 검증 (6개 좌표)

ODsay Lab 공식 사이트에서 `OPT=0, SearchType=0, SearchPathType=0, lang=0`으로 직접 호출해 검증(로컬 API 키가 IP 등록 방식이라 코드로는 호출 불가 → 공식 사이트 직접 테스트).

| # | 구간 | 직선거리 | 결과 |
|---|---|---|---|
| 1 | 서울역↔인천공항 | 60km | 61분(공항철도 직통) — TMAP(61.1분)·카카오(61분)와 거의 동일 |
| 2 | 홍대입구역↔종로3가역 | 6km | 1위 21분, 정렬 이슈 없음(TMAP·카카오는 1위가 실제 최단이 아닌 정렬 문제 있었음) |
| 3 | **강남역↔정자역** (핵심) | 16km | **신분당선 직통 20분** — 정상. 예전 "고속버스 30분"이 SearchType=1 강제 테스트의 인공물이었음이 최종 확인됨 |
| 4 | 일산(정발산)↔판교 | 41km, 경기↔경기 | 87분, 정상(서울 미경유 장거리 조합도 문제없음) |
| 5 | 부평(인천)↔수원 | 35km, 인천↔경기 | 73분, 정상 |
| 6 | [대조군] 연천↔평택 | 120km, 70km 훨씬 초과 | **에러 없음** — 208분(수도권 1호선만으로 완주) |

**6번(대조군)에서 얻은 예상 밖의 결론**: "70km 넘으면 SearchType=0이 깨진다"는 가설은 이 구간에서 틀렸다 — 연천·평택이 둘 다 수도권 1호선(경원선 연장) 노선으로 물리적으로 이어져 있어서 도시내 탐색만으로도 정상 응답이 나왔다. 즉 70km 임계값은 "API가 에러 나는 걸 막는 안전선"이 아니라, **"이 거리부터는 시외버스 등 도시간 교통수단을 SearchType=1로 따로 찾아야 더 빠른 경로를 놓치지 않는다"는 효율 기준**으로 재해석해야 한다(6번 결과도 "틀린 답"은 아니지만 3시간28분짜리 비효율적인 경로였음).

## 5. ODsay `searchPubTransPathT` 정확한 커버리지 범위

이 API(GoNow가 실제로 호출하는 엔드포인트)가 반환하는 건 `trafficType` 세 가지뿐이다: **지하철(1) · 버스(2) · 도보(3)**. 고속버스/시외버스(터미널 발권형)·KTX/무궁화 등 철도·항공은 이 API에 아예 안 나온다 — ODsay가 완전히 별도의 API로 제공한다(`search_inter_bus_schedule`, `search_intercity_bus_terminals`, `search_express_bus_terminals`, `search_train_service_time`, `search_air_service_time`).

버스 세부 종류 코드(ODsay 공식): `1`일반 `2`좌석 `3`마을버스 `4`직행좌석 `5`공항버스 `6`간선급행 `10`외곽 `11`간선 `12`지선 `13`순환 `14`광역(M버스 등) `15`급행 `16`관광버스 `20`농어촌버스 `22`경기도 시외형버스 `26`급행간선 `30`한강버스.

두 가지 헷갈릴 수 있는 지점을 실측으로 정리:
- **`22`(경기도 시외형버스)**: 이름과 달리 터미널 발권이 필요 없는 정류장 승하차형 버스. 실측 예시(8839번, 에버랜드↔인천터미널, 정류장 53개, 배차간격 50분)로 확인.
- **버스명에 붙는 "(예약)" 표기**(예: `1241(예약)`, `1500(예약)`, `M7412(예약)`): 경기도 광역버스 좌석예약제 — 선택 옵션이라 예약 없이도 일반 승차 가능. 강제 예약 아님.

**결론**: `searchPubTransPathT`가 반환하는 모든 후보는 구조적으로 예약 불필요 승하차형이다. GoNow의 `TransitType`(SUBWAY/BUS/ALL) 스코프와 정확히 일치하며, "예약 필요한 교통수단이 섞여서 잘못된 답을 준다"는 리스크는 이 API 구조상 원천적으로 없다.

## 참고 — 관련 문서

카카오맵 TRANSIT 딥링크 기능의 `PriorityType` 설계(카카오맵 자체 정렬 옵션과의 1:1 매칭, `MIN_WAIT`/동점 시 계단식 정렬 포함)와 이 조사에서 나온 SearchType/OPT 버그 수정 경위는 `reference/kakao-map-deeplink-spec.md` §2.4·§4.4~4.6, `history/resolved-bugs.md`의 버그31~33 참고 — 이 문서(계산 엔진 자체 비교)와는 다른 각도(딥링크 파라미터 설계)에서 같은 ODsay 조사를 다룬다.
