# GoNow 지도 딥링크 — 카카오맵 공식 스펙 + 구현 가이드

[feature-ideas.md](../planning/feature-ideas.md) 아이디어 A(지도 연동)의 구현 상세를 전부 여기로 모았다 — 카카오맵 공식 스펙 원문부터, GoNow가 그 위에서 실제로 어떻게 쓸지에 대한 설계 결정, 그리고 실측으로 검증한 것들까지 이 문서 하나로 완결됨.

---

## 1부 — 카카오맵 공식 딥링크 스펙 (참고 자료)

### 1.1 길찾기(내비게이션) — 앱 / 모바일웹 URL Scheme

좌표로 출발지·경유지(최대 5개, `vp`~`vp5`)·목적지를 지정해서 이동수단별 길찾기를 바로 실행. **대중교통은 경유지 미지원.**

| 버전 | 종류 | URL 형식 |
|---|---|---|
| 6.0.0+ | 앱 | `kakaomap://route?sp={위도},{경도}&ep={위도},{경도}&by={이동수단}` |
| 6.0.0+ | 모바일웹 | `http://m.map.kakao.com/scheme/route?sp={위도},{경도}&ep={위도},{경도}&by={이동수단}` |

- 이동수단 값(**소문자**): `car`, `publictransit`, `foot`, `bicycle`
- 예시(도보 + 경유지 1개): `kakaomap://route?sp=37.40205,127.10821&vp=37.39424,127.11030&ep=37.39529,127.11044&by=foot`
- 순수 십진수 좌표만 쓰고 별도 인코딩 불필요 — 앱 버전과 모바일웹 버전이 파라미터 구조까지 동일함.

### 1.2 길찾기 바로가기 — 공유 링크(`/link/...`)

좌표(이름,위도,경도) 또는 카카오 장소ID로 경로 공유 링크 생성. 경유지 최대 5개, **대중교통(`traffic`)은 경유지 미지원.**

| URL 패턴 | 설명 |
|---|---|
| `/link/to/이름,위도,경도` | 목적지만 지정(출발지는 현재 위치로 추정) |
| `/link/to/장소ID` | 장소ID로 목적지 지정 |
| `/link/from/이름,위도,경도/to/이름,위도,경도` | 출발지+목적지 (이동수단 지정 불가 — 항상 자동차 기본값) |
| `/link/by/{이동수단}/이름,위도,경도/이름,위도,경도` | 출발지+목적지+이동수단 지정 |
| `/link/by/{이동수단}/이름,위도,경도/이름,위도,경도/이름,위도,경도` | 출발지+경유지+목적지+이동수단 |
| `/link/by/subway/{지역명}/출발역명/도착역명` | 지하철 노선도 길찾기(`seoul`/`busan`/`daegu`/`gwangju`/`daejeon`) |

- 이동수단 값(이 패턴 전용, **1.1과 다른 값**이니 혼동 주의): `car`, `traffic`(대중교통 — 1.1의 `publictransit`과 다름), `walk`(1.1의 `foot`과 다름), `bicycle`

## 2부 — GoNow 딥링크 기능 설계

### 2.1 언제·어디에 노출할지

**어느 상태에서 노출할지 — 상태 전이도 기준**: `SCHEDULED`/`READY`/`ARRIVED`에서는 의미가 없다(아직 나갈 때가 아니거나 이미 도착함). 실제로 길찾기가 필요한 구간은 `DEPARTING`(지금 나가라는 신호가 뜨는 순간) → `MOVING`(실제로 이동하며 길을 찾아가는 중, 오히려 헷갈리는 게 이 구간) → `NEARDEST`(거의 도착, 정확한 입구 찾기)까지다. 각 알람 항목(`DailyAlarmScreen.tsx` 등에서 이미 `myStatus` 필드로 상태를 갖고 있음)을 기준으로 `DEPARTING`/`MOVING`/`NEARDEST`일 때만 버튼을 노출/활성화한다.

**어디에 노출할지 — 서로 보완하는 두 지점**:

| | 푸시 알림의 "길찾기" 액션 버튼 | 인앱 알람 카드의 "길찾기" 버튼 |
|---|---|---|
| 위치 | `DEPARTING` 단계별 출발 알람(1~4단계)이 상단바에 뜰 때, 그 알림에 붙는 액션 버튼 | 앱 안 알람 리스트 화면(날짜별/카테고리별)에서 각 알람을 나타내는 카드 UI에 상시 배치, `myStatus`가 `DEPARTING`/`MOVING`/`NEARDEST`일 때만 노출 |
| 역할 | 알림이 뜨는 그 순간 원터치로 바로 이동 | 알림을 놓치거나 실수로 지웠어도 앱만 열면 언제든 접근 가능한 안전망 — "알림 슬라이드 삭제" 문제를 실질적으로 해결하는 건 이쪽 |
| 구현 메모 | 알림 **몸체 탭**(`EventType.PRESS`)으로 바로 딥링크를 실행하려면 지금 없는 새 인프라가 필요함 — 대신 기존 도착확인/닫기 버튼과 같은 **액션 버튼**(`ACTION_PRESS`) 패턴을 재사용해서 "길찾기" 버튼을 하나 추가하는 쪽이 구현이 훨씬 쉬움 | 카드 렌더링에 `myStatus` 조건 + 버튼 하나 추가하는 수준 |

둘은 대체재가 아니라 보완 관계라 **둘 다 구현하는 걸 추천**한다.

### 2.2 목적지를 어디까지 잡을지 — 상황별 라우팅 규칙

최종 목적지로 고정하지 않고 상황에 따라 달라져야 한다. GoNow가 이미 갖고 있는 데이터만으로 판단 가능(`FlaskJourneyResponse`/`FlaskParticipantResponse`의 `whichStation`(최초 승차 정류장/역 이름, 좌표는 없음, DRIVING이면 null), `boardingTime`(탑승 예정 시각, DRIVING이면 null), `transportType`) — **새 백엔드 작업 없이 프론트 로직만으로 구현 가능**:

| 상황 | 딥링크 목적지 | 이유 |
|---|---|---|
| DRIVING 모드 | 항상 현재 위치 → **최종 목적지** | 경유 개념이 없고 `whichStation`/`boardingTime`도 항상 null이라 볼 필요조차 없음 |
| TRANSIT, 아직 탑승 전으로 추정(현재 시각 < `boardingTime`) | 현재 위치 → **`whichStation`(승차 정류장/역)** | 실제로 사람들이 헷갈리는 구간이자 GoNow가 이미 정밀 계산해둔 정보 — 탄 다음은 길찾기가 필요 없음 |
| TRANSIT, 탑승 이후로 추정(현재 시각 ≥ `boardingTime`) 또는 상태가 `NEARDEST` | 현재 위치 → **최종 목적지**로 자동 전환 | 이미 하차해서 걷는 중일 가능성이 높음 |

**"이미 승차지점을 지나쳤는데 딥링크를 누르면?"에 대한 답도 이 표에 들어있다** — `whichStation`은 좌표가 없어 "물리적으로 지나쳤는지"를 GPS로 직접 판단할 수는 없지만, 이미 계산되어 있는 `boardingTime`을 기준으로 "시간이 지났으면 탑승했을 것"이라고 추정해서 목적지 딥링크로 자동 전환하면 된다.

**정직하게 남겨야 할 한계 (과신하지 않기)**:
- 버스를 놓쳐서 `boardingTime`은 지났지만 실제로는 아직 정류장 근처에 있는 "지각" 케이스 — 이땐 목적지 딥링크로 전환되는 게 오히려 아쉬울 수 있다. 이건 아이디어 D(사후 지각 재알림)와 맞물리는 영역이라 이번 규칙의 범위 밖으로 남겨둠 — 추후 정밀화 필요.
- `whichStation`이 이름 문자열뿐이라, 카카오맵 쪽 장소 검색이 정확히 매칭 안 될 가능성(동명 정류장 등)이 있음 — 실제 구현 시 확인 필요.

## 4부 — 실측 검증 기록

### 4.1 그동안 확인/추측했던 것과 공식 스펙의 관계

- **앱 딥링크에 `by=CAR`/`by=PUBLICTRANSIT`(대문자)로 테스트했는데 정상 동작함** — 공식 문서는 소문자(`car`/`publictransit`)로 명시돼 있어서, 대문자는 카카오맵 앱이 관대하게 처리해준 것으로 보임. **소문자로 맞추는 게 안전.**
- `/actions/carRoute`, `/actions/publicRoute`, `sxEnc`/`syEnc`/`exEnc`/`eyEnc` 등(사용자가 카카오맵 웹사이트를 직접 조작하며 URL을 캡처해서 알아낸 값들)은 **이 공식 문서에 없는, 웹사이트 내부 구현 세부사항**으로 보임. 공식 스펙이 아니라 신뢰도가 낮고, 애초에 `sxEnc`류 인코딩 값은 우리가 만들어낼 방법이 없어서 막혀 있었음.
- **`http://m.map.kakao.com/scheme/route?sp=...&ep=...&by=...`(모바일웹 스킴)가 우리가 찾던 답이었음** — 앱과 동일한 순수 십진수 좌표 구조라, 이미 갖고 있는 데이터(검색 결과의 위도/경도)로 바로 만들 수 있었고, 실기기 검증도 완료됨(3부 참고).

### 4.2 `by=` 세분화 시도 결과 — 버스/지하철 단독 필터는 불가능 (실기기+PC 테스트로 확정)

GoNow의 회원 이동수단 선호(`TransitType`: `ALL`/`SUBWAY`/`BUS`)를 딥링크에도 그대로 반영할 수 있을지 테스트함.

- **전제 확인**: 카카오맵 대중교통 검색 결과 화면은 "전체"(버스만/지하철만/버스+지하철 조합을 다 합친 것) / "버스" / "지하철" / "버스+지하철" 4개 탭으로 나뉨. `by=publictransit`로 열면 항상 "전체" 탭이 뜨는데, 이건 GoNow의 `ALL`(상관없음)과 개념적으로 대응됨.
- **`by=bus`, `by=subway` 같은 비공식 값을 직접 테스트**(`m.map.kakao.com/scheme/route`에 동일 좌표로 `by=publictransit`/`by=bus`/`by=subway` 세 가지를 PC에서 열어 비교) — **셋 다 완전히 동일한 결과("전체" 탭)로 렌더링됨.** 즉 이 URL Scheme은 대중교통 내에서 버스/지하철을 구분해서 여는 기능 자체가 없음(1.1의 공식 4개 값 — `car`/`publictransit`/`foot`/`bicycle` — 이 정말 전부라는 게 실측으로도 재확인됨).
- **결론**: 딥링크 테스트 화면의 이동수단 버튼은 대중교통(`publictransit`)/자동차(`car`) 2개로 유지. `SUBWAY`/`BUS`/`ALL` 세분화는 딥링크가 아니라 **ODsay 기반 실제 경로 계산(Flask) 쪽에서 이미 담당하고 있는 역할**이라, 딥링크 단계에서 굳이 재현할 필요가 없음(딥링크는 "계산 다 끝난 뒤 지도로 보조 확인용"으로만 열리는 것이라 그 시점엔 이동수단 세분화가 의미 없음).

### 4.3 경로 우선순위(최소시간/최소환승/최소도보)도 딥링크로 지정 불가 — 추론(미실측)

GoNow의 회원 경로 우선순위 선호(`PriorityType`: `MIN_TIME`/`MIN_TRANSFER`/`MIN_WALK`)도 딥링크에 반영 가능한지 확인.

- 1.1·1.2의 공식 파라미터는 `sp`/`ep`/`vp`(경유지)/`by`(이동수단)가 전부이고, 정렬·우선순위 관련 파라미터는 애초에 스펙에 없음.
- 4.2에서 스펙에 없는 값(`by=bus`/`by=subway`)이 실제로도 안 먹히는 게 실측으로 확인된 전례가 있어서, 같은 패턴으로 우선순위 파라미터도 지원 안 될 것으로 추정 — **다만 이번 건은 4.2와 달리 PC/실기기로 직접 재테스트하지는 않은, 스펙 기반 추론 단계.** 필요하면 나중에 실측으로 재확인.
- **결론(4.2와 동일한 논리)**: 설령 안 되더라도 문제 없음 — `PriorityType` 선호는 딥링크가 아니라 **ODsay 기반 실제 경로 계산(Flask)에서 이미 반영되고 있는 값**이고, 딥링크는 그 계산이 끝난 뒤 지도로 보조 확인하는 용도라 여기서까지 재현할 필요가 없음. (근거는 아래 4.4 — 코드로 실제 확인됨.)

### 4.4 (근거 확인) `TransitType`/`PriorityType`이 실제로 ODsay 쿼리에 반영되는지 플라스크 코드로 검증

4.2·4.3의 "딥링크가 세분화 안 해줘도 상관없다"는 결론은 "그 세분화가 이미 앞단(ODsay)에서 처리되고 있다"는 전제에 기대고 있어서, 이 전제 자체를 플라스크 코드(`D:\gonow-flask`)로 직접 확인함.

**플라스크가 ODsay에 실제로 보내는 요청** (`transit_route.py`, `GET https://api.odsay.com/v1/api/searchPubTransPathT`):

| GoNow 설정 | ODsay 파라미터 | 매핑 | 상태 |
|---|---|---|---|
| `TransportMode`(대중교통 한정: `ALL`/`SUBWAY`/`BUS`) | `SearchType` | `ALL`=0, `SUBWAY`=1, `BUS`=2 | ✅ 완전히 연결됨 |
| `PriorityType`(`MIN_TIME`/`MIN_TRANSFER`/`MIN_WALK`) | `OPT` | `MIN_TIME`=0, `MIN_TRANSFER`=1, `MIN_WALK`=2 | ✅ 완전히 연결됨 |

- 정렬은 전부 ODsay가 처리 — 플라스크는 `OPT`/`SearchType`을 넘긴 뒤 ODsay가 돌려준 후보 경로 중 **첫 번째(`paths[0]`)를 그대로 사용**할 뿐, 자체적으로 재정렬/재비교하는 로직은 없음.
- 두 값 다 실제 프로덕션 흐름(`POST /internal/alarm/journey`, `POST /internal/alarm/appointment`)에서 Spring 요청 바디 → 플라스크 → ODsay 쿼리까지 끊김 없이 이어짐. 장식용으로 남아있는 미사용 설정이 아님.
- 예외 1: `SUBWAY`/`BUS`로 좁혀 검색했는데 결과가 없으면 `ALL`로 자동 폴백(CLAUDE.md에 이미 문서화된 정책과 일치).
- 예외 2: 레거시 엔드포인트 `POST /api/personal/departure`(현재 프로덕션 흐름에서 안 쓰는 것으로 보이는 구버전 경로)는 `priority_type`/이동수단 제한을 아예 안 받아서 항상 기본값(ALL/MIN_TIME)으로만 호출됨.

**결론**: 4.2·4.3에서 "딥링크가 이 선호도들을 반영 못 해도 문제없다"고 한 근거가 추측이 아니라 사실로 확인됨 — `TransitType`/`PriorityType`은 딥링크 단계가 아니라 그보다 훨씬 앞단인 ODsay 쿼리 자체에서 이미 실질적으로 작동하고 있음.

개발 중 ODsay 응답을 직접 조회하며 확인하고 싶을 땐 [odsay-mcp-guide.md](odsay-mcp-guide.md) 참고.
