# GoNow 지도 딥링크 — 카카오맵 공식 스펙 + 구현 가이드

[feature-ideas.md](../planning/feature-ideas.md) 아이디어 A(지도 연동)의 구현 상세를 전부 여기로 모았다 — 카카오맵 공식 스펙 원문부터, GoNow가 그 위에서 실제로 어떻게 쓸지에 대한 설계 결정, 그리고 실측으로 검증한 것들까지 이 문서 하나로 완결됨.

## 1부 — 카카오맵 공식 딥링크 스펙 (참고 자료)

### 1.1 길찾기(내비게이션) — 앱 / 모바일웹 URL Scheme

좌표로 출발지·경유지(최대 5개, `vp`~`vp5`)·목적지를 지정해서 이동수단별 길찾기를 바로 실행. **대중교통은 경유지 미지원.**

| 버전 | 종류 | URL 형식 |
|---|---|---|
| 6.0.0+ | 앱 | `kakaomap://route?sp={위도},{경도}&ep={위도},{경도}&by={이동수단}` |
| 6.0.0+ | 모바일웹 | `http://m.map.kakao.com/scheme/route?sp={위도},{경도}&ep={위도},{경도}&by={이동수단}` |

- 이동수단 값(**소문자**): `car`, `publictransit`, `foot`, `bicycle`
- 예시(도보 + 경유지 1개): `kakaomap://route?sp=37.40205,127.10821&vp=37.39424,127.11030&ep=37.39529,127.11044&by=foot`
- 순수 십진수 좌표만 쓰고 별도 인코딩 불필요 — 앱 버전과 모바일웹 버전이 파라미터 구조까지 동일함.

### 1.2 길찾기 바로가기 — 공유 링크(`/link/...`)

좌표(이름,위도,경도) 또는 카카오 장소ID로 경로 공유 링크 생성. 경유지 최대 5개, **대중교통(`traffic`)은 경유지 미지원.**

| URL 패턴 | 설명 |
|---|---|
| `/link/to/이름,위도,경도` | 목적지만 지정(출발지는 현재 위치로 추정) |
| `/link/to/장소ID` | 장소ID로 목적지 지정 |
| `/link/from/이름,위도,경도/to/이름,위도,경도` | 출발지+목적지 (이동수단 지정 불가 — 항상 자동차 기본값) |
| `/link/by/{이동수단}/이름,위도,경도/이름,위도,경도` | 출발지+목적지+이동수단 지정 |
| `/link/by/{이동수단}/이름,위도,경도/이름,위도,경도/이름,위도,경도` | 출발지+경유지+목적지+이동수단 |
| `/link/by/subway/{지역명}/출발역명/도착역명` | 지하철 노선도 길찾기(`seoul`/`busan`/`daegu`/`gwangju`/`daejeon`) |

- 이동수단 값(이 패턴 전용, **1.1과 다른 값**이니 혼동 주의): `car`, `traffic`(대중교통 — 1.1의 `publictransit`과 다름), `walk`(1.1의 `foot`과 다름), `bicycle`

## 2부 — GoNow 딥링크 기능 설계

### 2.1 언제·어디에 노출할지

**어느 상태에서 노출할지 — 최종 확정: `READY`/`DEPARTING`/`MOVING`/`NEARDEST` 4개 상태 전부 (2026-08-18 재검토 후 확대)**

초기 설계는 `DEPARTING`(지금 나가라는 신호가 뜨는 순간) → `MOVING`(실제로 이동하며 길을 찾아가는 중)까지만 노출하고, `SCHEDULED`/`READY`/`ARRIVED`는 "아직 나갈 때가 아니거나 이미 도착함"이라는 이유로, `NEARDEST`(목적지 100m 이내)는 "이미 코앞이라 실용성이 낮다"는 이유로 제외했었다. 이후 재검토 결과:

- **`READY` 포함**: 출발 시각에 맞춰 나가는 게 기본 전제지만, 더 일찍 출발하고 싶은 사용자도 있다. 버튼이 없어도 사용자가 카카오맵을 직접 열어 검색하면 어차피 할 수 있는 일이라, 버튼 추가는 새 능력이 아니라 편의성일 뿐이고 상태머신에도 영향 없다(GoNow는 GPS/지오펜스로만 이동을 판단하지 "버튼을 눌렀는지"와는 무관). `SCHEDULED`/`ARRIVED`는 여전히 제외(각각 "아직 당일 아님"/"이미 종료").
- **`NEARDEST` 포함**: 출발지-목적지가 매우 가까울 때(카카오모빌리티 REST API 기준 5m 이내는 `result_code 104`로 명시적 거부, 버그48 참고) 카카오맵이 어떻게 반응하는지가 유일한 우려였는데, 실측 결과(웹 map.kakao.com + 안드로이드 네이티브 앱 둘 다) 에러나 빈 화면이 아니라 "출발지와 도착지가 같은 곳이에요. 다른 곳으로 설정해주세요"라는 친절한 안내 메시지로 정상 처리되는 것을 확인했다. 노출 안 할 이유가 사라짐.

각 알람 항목(`DailyAlarmScreen.tsx` 등에서 이미 `myStatus` 필드로 상태를 갖고 있음)을 기준으로 4개 상태 전부에서 버튼을 활성화한다 — `src/utils/kakaoMapDeeplink.ts`의 `NAVIGABLE_STATUSES` 참고.

**렌더링 방식(2026-08-18 재조정)**: `SCHEDULED`/`ARRIVED`일 때 버튼을 아예 숨기던 것에서, **항상 렌더링하되 비활성 상태만 회색으로 표시**하는 방식으로 바꿨다 — 배경색 `#EAF2FB`→`#EEEEEE`, 아이콘 색 `#4A90D9`→`#CCCCCC`, `disabled` 처리(누르면 아무 동작 안 함). 버튼이 매번 사라졌다 나타나면 레이아웃이 흔들리고, 사용자가 "왜 없어졌지"보다 "지금은 비활성 상태구나"를 더 직관적으로 파악할 수 있다는 이유. 6곳(`DailyAlarmScreen.tsx` 3곳 + `Personal/Home/GroupAllAlarmSheet.tsx` 각 1곳) 전부 동일 패턴 — 각 파일 `navigateBtnDisabled` 스타일 참고. 로딩 중(GPS 확보 대기)에는 아이콘 대신 `ActivityIndicator`를 같은 자리에 표시하는 것도 이번에 같이 추가됨(카드별 `navigatingId` 상태로 관리, 다른 카드에 영향 없음).

**GPS 캐시 정책도 함께 재검토 끝에 완전히 제거됨**: 애초 설계는 "DEPARTING/MOVING 둘 다 앱이 GPS를 짧은 주기로 폴링 중이라 OS 캐시가 신선하다"는 전제로 DEPARTING 60초/MOVING 20초 캐시를 뒀었다. 그런데 2026-08-17 지오펜싱 마이그레이션으로 DEPARTING도 폴링이 아니라 순수 지오펜싱으로 바뀌면서 이 전제가 깨졌고(`journey-state-machine.md` 참고 — 안드로이드에서 실제로 폴링을 유지하는 상태는 MOVING 하나뿐), MOVING도 폴링 주기가 3초~5분으로 가변적이라 고정된 20초 캐시가 실제 주기와 안 맞을 수 있다는 문제가 남았다. 상태별로 캐시 시간을 정교하게 나누는 방안(실제 저장된 interval 값을 조회해서 쓰는 안 등)도 검토했으나, **이 버튼은 애초에 사용자가 어쩌다 한 번 누르는 수동 액션이라 캐시로 아낄 수 있는 몇 초가 최적화할 가치가 없다고 결론** — `NAVIGATE_CACHE_MAX_AGE_MS`/캐시 우선 로직 자체를 제거하고, 4개 상태 전부 `openKakaoMapRoute()`가 매번 `Location.getCurrentPositionAsync()`로 새로 GPS를 잡도록 통일했다. 기왕 매번 새로 잡는 김에 정확도도 기존 기본값(`Balanced`, ~100m 오차)에서 `Accuracy.High`로 올림 — NEARDEST 100m/카카오 5m 거부 경계(버그48) 같은 좁은 임계값들과 비교하면 Balanced의 오차는 무시하기 어려운 수준이라 판단.

**대중교통 700m 미만이면 도보(`foot`)로 자동 전환(2026-08-18 추가)**: `publictransit` 모드일 때만, GPS로 잡은 현재 위치와 목적지 사이 직선거리(haversine)가 700m 미만이면 `by=publictransit` 대신 `by=foot`으로 딥링크를 연다. 700m는 새로 정한 값이 아니라 플라스크 `walk_fallback()`(`gps_api/core/transit_route.py`의 `SHORT_DISTANCE_THRESHOLD_M`)과 동일한 기준을 그대로 재사용한 것 — 그 거리 이하면 ODsay 대중교통 검색 자체가 무의미하다고 이미 백엔드가 판단하는 값이라 프론트 딥링크 판단도 일치시킴. `car`(자가용)는 대상에서 제외 — 자차가 있는데 도보를 권할 이유가 없음. `by=foot`은 1.1절 공식 스펙에 이미 있는 값이라 신규 URL 파라미터 조사 없이 그대로 사용 가능했음.

**어디에 노출할지 — 서로 보완하는 두 지점**:

| | 푸시 알림의 "길찾기" 액션 버튼 | 인앱 알람 카드의 "길찾기" 버튼 |
|---|---|---|
| 위치 | `DEPARTING` 단계별 출발 알람(1~4단계)이 상단바에 뜰 때, 그 알림에 붙는 액션 버튼 | 앱 안 알람 리스트 화면(날짜별/카테고리별)에서 각 알람을 나타내는 카드 UI에 상시 배치, `myStatus`가 `DEPARTING`/`MOVING`일 때만 노출 |
| 역할 | 알림이 뜨는 그 순간 원터치로 바로 이동 | 알림을 놓치거나 실수로 지웠어도 앱만 열면 언제든 접근 가능한 안전망 — "알림 슬라이드 삭제" 문제를 실질적으로 해결하는 건 이쪽 |
| 구현 메모 | 알림 **몸체 탭**(`EventType.PRESS`)으로 바로 딥링크를 실행하려면 지금 없는 새 인프라가 필요함 — 대신 기존 도착확인/닫기 버튼과 같은 **액션 버튼**(`ACTION_PRESS`) 패턴을 재사용해서 "길찾기" 버튼을 하나 추가하는 쪽이 구현이 훨씬 쉬움 | 카드 렌더링에 `myStatus` 조건 + 버튼 하나 추가하는 수준 |

둘은 대체재가 아니라 보완 관계라 **둘 다 구현하는 걸 추천**한다.

### 2.2 목적지를 어디까지 잡을지 — 최종 확정: 항상 최종 목적지 (단일 딥링크)

**한때는 "탑승 전엔 `whichStation`(정류장), 탑승 후엔 최종 목적지"로 상황별 분기하는 설계였으나, 아래 논의 끝에 완전히 폐기하고 DRIVING과 동일하게 "항상 현재 위치 → 최종 목적지" 단일 딥링크로 확정했다.** 이유는 다음 절(2.3)에 상세히 정리한다. 이 결정으로 `whichStation`의 좌표가 없다는 문제(2.2 구버전에서 실제 구현을 막던 블로커였음) 자체가 무의미해졌다 — 애초에 정류장 좌표가 필요 없는 설계가 됐기 때문이다.

### 2.3 TRANSIT 딥링크 설계 — 왜 "여러 구간별 딥링크"가 아니라 "단일 딥링크"인가

#### 검토했던 대안들

카카오맵 대중교통 길찾기는 **경유지 개념이 없다**(1.1절 참고 — `by=publictransit`은 `vp` 경유지 파라미터를 지원 안 함). 그래서 "ODsay가 계산한 다구간 경로(도보→버스→환승→지하철→도보)를 딥링크로 어떻게 정확히 반영할까"를 두고 세 가지 안을 검토했다:

- **안 A — 구간별 멀티 딥링크 버튼**: ODsay `subPath`의 각 구간(도보 이동 포함)마다 좌표를 뽑아서, "1단계: 집→첫정류장", "2단계: 첫정류장→환승지", "3단계: 환승지→최종목적지" 식으로 버튼을 여러 개 만들어 순서대로 누르게 하는 방식. 구간이 끝날 때마다 GoNow 앱으로 돌아와 다음 버튼을 눌러야 함.
- **안 B — 단일 딥링크(현재 위치 → 최종 목적지)**: DRIVING과 동일하게 좌표 2개만 넘기고, 카카오맵이 자체적으로 계산한 전체 대중교통 경로(버스/지하철/혼합 리스트)를 유저가 카카오맵 화면에서 직접 골라 이용하게 하는 방식.
- **안 C — 텍스트 브리핑 카드**: 지도/딥링크 대신 "OO역(4호선) → 환승 → OO역(3호선)" 같은 동선을 텍스트로만 보여주는 방식. 액션(버튼 눌러서 바로 안내 시작)이 없어 A/B와는 결이 다른 보조 수단으로 분류.

#### 최종 결론: 안 B (단일 딥링크) 채택 — 근거

1. **UX**: 안 A는 이동 중 앱↔카카오맵을 구간마다 왕복해야 해서 피로도가 높고, 카카오맵 자체 내비게이션의 연속 안내(환승까지 한 화면에서 턴바이턴)가 끊긴다. 안 B는 한 번의 딥링크로 전체 여정에 대한 카카오맵의 완전한 길찾기 화면(버스/지하철/혼합 탭 포함)을 그대로 활용한다.
2. **정확도 재현은 애초에 완벽할 수 없다**: 안 A로 구간을 아무리 잘게 쪼개도, 카카오맵은 그 구간에 대해서도 **자기 자신의 엔진으로 다시 계산**한다(딥링크는 좌표만 넘길 뿐 "이 노선을 타라"고 강제할 파라미터가 없음 — 4.3절 기존 결론과 동일). 즉 안 A는 "일치 확률을 높이는 것"이지 "일치를 보장하는 것"이 아니다. 반면 실측(4부)상 후보 간 시간 차이는 대부분 1~10분 수준이라, 이 잔여 불일치의 실제 크기 자체가 작다.
3. **제품 철학과의 정합성**: GoNow의 역할은 "정확한 출발 시각을 계산해서 알려주는 것"이지 "턴바이턴 내비게이션을 대체하는 것"이 아니다(DRIVING 딥링크도 처음부터 이 철학). DEPARTING 이후 유저가 GoNow가 가정한 경로와 다르게 이동해서 지각하더라도, 이는 GoNow가 책임지는 범위 밖으로 명시적으로 합의됨 — 이 전제하에 안 A가 주는 유일한 이점(경로 일치도)의 실익이 사라진다.
4. **개발 비용**: 안 B는 DRIVING 딥링크 인프라(`openKakaoMapRoute()`, 버튼 UI, 캐시 로직)를 그대로 재사용 가능하고 신규 백엔드 작업이 0에 가깝다. 안 A는 Flask가 구간별 좌표를 새로 응답에 실어야 하고(`TransitLeg`는 현재 폴리라인 전체만 갖고 있어 시작/끝 좌표를 별도 추출해야 함), Spring DTO 확장, 프론트 다중 버튼 상태 관리까지 필요해 스코프가 크다. 대회 제출까지 3주 남은 시점에 감당하기 부담스러움.
5. **부수 효과**: 안 B를 채택하면 그동안 구현을 막고 있던 "`whichStation` 좌표 없음" 블로커가 통째로 사라진다(2.2절 참고) — 목적지 좌표는 여정 생성 시점부터 이미 DB에 있는 값이라 신규 조회가 필요 없다.

안 C(텍스트 브리핑)는 폐기하지 않고 "필요하면 나중에 추가하는 보조 정보"로 남겨둔다 — 딥링크 버튼과 별개로, 단계별 알람 문구에 `whichStation`/`boardingTime`을 텍스트로만 노출하는 것은 여전히 가치가 있으나 이번 스코프에서는 제외.

### 2.4 TRANSIT 우선순위 옵션(PriorityType) 설계 — "경로 지정"이 아니라 "소요시간 추정 개인화"

안 B를 채택하면 GoNow가 계산한 특정 후보 경로를 유저가 그대로 따라간다는 보장이 없다(카카오맵에서 유저가 자유롭게 고름). 그래서 `PriorityType`(회원 설정)의 의미를 다음과 같이 명확히 재정의한다:

> **`PriorityType`은 "이 경로로 안내하겠다"는 지정이 아니라, "이 유저는 평소 이동할 때 무엇을 중요하게 여기는가"를 반영해 소요시간 추정치(그리고 그로부터 역산되는 출발 알람 시각)를 그 유저에게 맞게 개인화하는 입력값이다.** 예: 도보를 싫어하는 유저가 `MIN_WALK`를 설정하면, GoNow는 "도보 적은 경로 기준" 소요시간으로 알람을 계산한다 — 실제로 그 유저가 카카오맵을 열어도 본능적으로 도보 적은 옵션을 고를 가능성이 높으므로, 계산 기준과 실제 행동이 자연스럽게 맞아떨어진다.

이 재정의가 성립하려면 **유저가 카카오맵으로 넘어갔을 때 그 성향에 맞는 정렬 버튼을 실제로 누를 수 있어야 한다.** 그래서 카카오맵 자체 정렬 옵션(실제 화면 실측: 추천순/최단시간순/최소대기순/최소도보순/최소환승순)과 GoNow의 `PriorityType`을 1:1로 맞춘다:

| GoNow `PriorityType` | 카카오맵 대응 버튼 | ODsay 판단 기준(1순위 재정렬 키) |
|---|---|---|
| `MIN_TIME` | 최단시간순 | `info.totalTime` 최솟값 |
| `MIN_TRANSFER` | 최소환승순 | `info.busTransitCount + info.subwayTransitCount` 최솟값 |
| `MIN_WALK` | 최소도보순 | `info.totalWalk` 최솟값 |
| `MIN_WAIT` | 최소대기순 | `info.totalIntervalTime` 최솟값(배차간격 합) |

1순위가 동점인 후보가 여러 개면 2순위(`totalTime`, 이미 1순위인 경우는 건너뜀) → 나머지는 환승→도보→대기 순으로 계단식으로 정렬해 결정한다(상세는 `docs/history/resolved-bugs.md`의 버그33 "2026-08-08 추가" 항목 참고).

**검토했다가 제외한 옵션들과 이유**:
- **`MIN_COST`(최소요금)**: `info.payment` 필드로 기술적 구현은 가능하나, **카카오맵/네이버지도 둘 다 "요금순" 정렬 버튼 자체가 없다.** 유저가 GoNow에서 이 성향을 설정해도 카카오맵에서 재현할 방법이 없어(후보를 일일이 눈으로 비교해야 함) 위 표의 "계산 기준 = 실제 행동" 논리가 깨진다. 도시내 이동에서는 통합환승할인 때문에 요금 차이가 미미하기도 함. 다만 도시간(시외) 이동에서는 KTX vs 무궁화호 등 요금 차이가 실측상 유의미(최대 30%, 실측 4,700원)했다는 점은 기록해둔다 — 향후 카카오맵이 요금순 정렬을 지원하게 되거나, 시외 전용 별도 UI를 만들 가치가 생기면 재검토.
- **`RECOMMENDED`(추천순)**: 카카오맵의 "추천순"과 ODsay `OPT=0`의 "추천경로"는 서로 다른 회사의 서로 다른(공개 안 된) 내부 알고리즘이라 완전히 재현 불가능(4.5절 실측 참고). 이름이 주는 기대("똑똑한 추천")에 비해 실체가 부실해 신뢰도 측면에서도 제외.

**중요한 재확인**: DEPARTING 이후 유저가 GoNow가 가정한 경로와 다르게 이동해서 지각하더라도 GoNow 책임 범위 밖이다(2.3절 근거3). `PriorityType`의 가치는 "경로를 강제/보장"하는 데 있지 않고, 유저별로 더 정확한 출발 시각을 계산해주는 데 있다.

#### 참고: `departureAlarmTime` 계산에서 도보시간·준비시간의 위치 (`gonow-flask`, `alarm.py`)

```python
duration_sec, walk_min, ... = _transit_duration(...)   # ODsay totalTime — 첫 정류장까지 도보 포함 전체 door-to-door 시간
departure_time       = target_time - timedelta(seconds=duration_sec)      # "신발 신고 나가야 하는" 시각
departure_alarm_time = departure_time - timedelta(minutes=total_buffer_min)  # 여기서 알람이 울림
boarding_dt           = departure_time + timedelta(minutes=walk_min)      # 실제 탑승 시각
```

`duration_sec`(ODsay `totalTime`)에는 **첫 정류장까지의 도보 시간이 이미 포함**돼 있다. `total_buffer_min`(≈`preparationTime`)은 `departure_time`에서 한 번 더 빼는 **순수 준비 시간(옷 입기/씻기 등)**이며 도보 시간과는 완전히 별개다. 즉 알람이 울리는 시점(`departureAlarmTime`)부터 준비 → 신발 신고 출발(`departure_time`) → 도보 → 탑승(`boardingTime`) 순으로 이어지는 구조다.

## 3부 — 구현 진행 상황

1. ✅ 앱 딥링크의 `by=` 값을 소문자로 수정(`CAR`→`car`, `PUBLICTRANSIT`→`publictransit`) — `KakaoMapTestScreen.tsx` 반영 완료.
2. ✅ 웹 폴백을 `http://m.map.kakao.com/scheme/route?sp=...&ep=...&by=...`로 교체 — `KakaoMapTestScreen.tsx` 반영 완료. **모바일 실기기로 카카오맵 앱 설치/삭제 두 상태 모두 재검증 완료(사용자 확인)** — 출발지/도착지 자동 입력 포함 정상 동작.
3. ✅ **DRIVING(자가용) 전용 인앱 알람 카드 버튼 구현 완료, 실기기 검증 완료** — `src/utils/kakaoMapDeeplink.ts`의 `openKakaoMapRoute()`를 개인/그룹/귀가 알람 카드 4곳(`DailyAlarmScreen.tsx`, `PersonalAllAlarmSheet.tsx`, `HomeAllAlarmSheet.tsx`, `GroupAllAlarmSheet.tsx`)에서 공통 사용. `myStatus`가 `DEPARTING`/`MOVING`일 때만 버튼 노출(`NEARDEST`는 제외 — 이미 목적지 100m 이내라 자가용 길찾기 딥링크의 실용성이 낮다고 판단).
4. **GPS 조회 속도 최적화 — `getLastKnownPositionAsync()` 캐시 우선 사용**: 버튼 탭마다 `getCurrentPositionAsync()`로 매번 새 GPS 픽스를 잡으면 몇 초씩 딜레이가 생김(실기기 테스트로 확인됨). 앱이 이미 이 여정에 대해 GPS 폴링을 계속 돌리고 있으므로, OS가 캐싱해둔 최근 위치(`getLastKnownPositionAsync`)를 먼저 쓰고 없거나 오래됐을 때만 새로 요청하도록 변경. 캐시 유효기간(`maxAge`)은 상태별로 차등(`NAVIGATE_CACHE_MAX_AGE_MS`): `DEPARTING`(사실상 정지 상태) 60초, `MOVING`(실제 이동 중) 20초. 폴링 엔진의 실시간 `interval` 값을 동적으로 끌어다 쓰는 방안도 검토했으나, 물리적으로 짧은 시간(1분 이내) 동안의 이동 거리는 경로 자체를 무너뜨릴 정도가 아니고(고속도로 기준 최대 1~1.6km, 경로 방향은 유지됨), 이 버튼의 목적이 위치 정밀 기록이 아니라 빠른 화면 전환이라는 점에서 상태 기반 2단계 구분만으로 충분하다고 판단해 기각 — 새 연동 지점을 늘리는 데 따르는 엣지케이스/버그 위험 대비 이득이 작음.
5. ✅ **푸시 알림 "길찾기" 액션 버튼 구현 완료** — `notifications.ts`의 `scheduleFutureAlarm()`이 자가용 알람이면 `android.actions`에 길찾기 액션(1~3단계는 기존 "✕ 닫기" 옆에, 4단계는 원래 액션이 없었어서 단독으로) 추가. 백그라운드(`notifications.ts`의 `onBackgroundEvent`)/포그라운드(`app/_layout.tsx`의 `onForegroundEvent`) 양쪽에 `actionId === 'navigate'` 분기 추가, 인앱 카드 버튼과 동일한 `openKakaoMapRoute()` 재사용.
6. ✅ **헤드리스(백그라운드) 경로 좌표 누락 버그 발견 및 수정** — 딥링크 버튼을 눌러 카카오맵으로 전환되면 GoNow가 백그라운드로 밀려나는데, 이때 `alarmService.ts`(포그라운드 폴링)가 아니라 `backgroundLocationTask.ts`(헤드리스 폴링)가 대신 `/location`을 호출한다. `/location` 응답엔 목적지 좌표가 없어서(안 바뀌는 값이라 매번 안 실어줌), 이 경로가 남은 단계 알림을 재등록할 때(`syncStagedAlarms()`의 지문 비교 후 재등록 로직) 좌표 없이 덮어써서 **딥링크 버튼을 누른 시점 이후 단계부터 버튼이 사라지는** 버그가 실기기 테스트로 발견됨. 앱이 오래(약 30초 이상) 백그라운드에 머물러야 헤드리스 경로가 실제로 `/location`을 호출할 기회가 생겨서, 짧게 왔다갔다하는 테스트로는 재현이 들쭉날쭉했음. **수정**: `backgroundLocationTask.ts`에 `ALARM_NAV_INFO_KEY`(AsyncStorage) 신설 — `alarmService.ts`의 `AlarmRunner.start()`가 목적지 좌표/이동수단/막차여부를 저장해두고(`stop()` 시 삭제), 헤드리스 폴링 루프가 이 값을 읽어서 `syncStagedAlarms()`에 그대로 전달. AsyncStorage 기반이라 프로세스가 완전히 종료돼도 값이 유지되므로, 애초에 범위 밖으로 뺐던 "앱 완전 종료" 케이스까지 결과적으로 함께 해결됨.
7. ✅ **TRANSIT(대중교통) 모드 확장 완료** — 최종 설계는 2.3/2.4절 참고: 구간별 멀티 딥링크(안 A)가 아니라 DRIVING과 동일한 단일 딥링크(안 B, 현재 위치→최종 목적지)로 확정, `PriorityType`은 `MIN_TIME`/`MIN_TRANSFER`/`MIN_WALK`/`MIN_WAIT` 4개로 카카오맵 자체 정렬 옵션과 1:1 매칭(`MIN_COST`/`RECOMMENDED`는 검토 후 제외). 이 결정으로 이전에 블로커였던 `whichStation` 좌표 문제 자체가 무의미해짐. 구현 완료 내역: (1) Flask `fetch_transit_route()`에 `MIN_WAIT` 재정렬 키(`totalIntervalTime`) + 동점 시 계단식 정렬 추가, (2) Spring `PriorityType` enum에 `MIN_WAIT` 추가, (3) 프론트 `isDriving: boolean` → `transportMode: 'car' | 'publictransit'` 배선 전체 교체로 TRANSIT도 `openKakaoMapRoute()`를 `by='publictransit'`로 공유(신규 좌표 조회 불필요, 여정의 기존 목적지 좌표 그대로 사용). **인앱 카드 버튼(날짜별 + 전체보기 화면) + 푸시 알림 액션 버튼(상단바 알림) 모두 실기기 노출·동작 확인 완료**(아래 10번 참고).

10. ✅ **실기기 테스트 중 전체보기 화면 3곳의 딥링크 버튼 누락 버그 발견 및 수정** — `PersonalAllAlarmSheet.tsx`/`HomeAllAlarmSheet.tsx`/`GroupAllAlarmSheet.tsx`(개인/귀가/그룹 전체보기 리스트)는 `DailyAlarmScreen.tsx`와 별개로 자체 `canNavigate`/`handleNavigate`를 갖고 있었는데, `transportMode` 배선 교체 작업에서 이 3곳만 빠뜨려서 TRANSIT 알람에서만 딥링크 버튼이 안 뜨는 버그가 실기기 테스트로 발견됨(날짜별 리스트에선 정상 노출). `DailyAlarmScreen.tsx`와 동일한 방식(`canNavigate`에서 `transport==='car'` 조건 제거, `handleNavigate`에 `toTransportMode()` 적용)으로 수정 후 재테스트로 정상 노출 확인.
8. ✅ **UX 문구 다듬기 완료** — "✕ 닫기" → "✕ 이후 알림 끄기"(실제 동작이 "남은 단계 전체 취소"라는 걸 명확히 전달), 1~3단계를 건너뛰고 바로 4단계가 발송되는 경우 제목을 "🔴 임계 구간"(단계를 거쳐 도달했다는 뉘앙스) 대신 "🔴 지각 구간"으로 분기, "이후 알림 끄기" 버튼을 누르면 포그라운드에서 토스트로 확인 피드백(백그라운드는 안 함 — 헤드리스 컨텍스트에서 지연 취소되는 알림을 새로 만드는 게 오히려 알림이 안 지워지고 계속 남을 위험이 있어 기각, 대신 눌린 그 알림이 상단바에서 사라지는 것 자체로 충분하다고 판단).

## 4부 — 실측 검증 기록

### 4.1 그동안 확인/추측했던 것과 공식 스펙의 관계

- **앱 딥링크에 `by=CAR`/`by=PUBLICTRANSIT`(대문자)로 테스트했는데 정상 동작함** — 공식 문서는 소문자(`car`/`publictransit`)로 명시돼 있어서, 대문자는 카카오맵 앱이 관대하게 처리해준 것으로 보임. **소문자로 맞추는 게 안전.**
- `/actions/carRoute`, `/actions/publicRoute`, `sxEnc`/`syEnc`/`exEnc`/`eyEnc` 등(사용자가 카카오맵 웹사이트를 직접 조작하며 URL을 캡처해서 알아낸 값들)은 **이 공식 문서에 없는, 웹사이트 내부 구현 세부사항**으로 보임. 공식 스펙이 아니라 신뢰도가 낮고, 애초에 `sxEnc`류 인코딩 값은 우리가 만들어낼 방법이 없어서 막혀 있었음.
- **`http://m.map.kakao.com/scheme/route?sp=...&ep=...&by=...`(모바일웹 스킴)가 우리가 찾던 답이었음** — 앱과 동일한 순수 십진수 좌표 구조라, 이미 갖고 있는 데이터(검색 결과의 위도/경도)로 바로 만들 수 있었고, 실기기 검증도 완료됨(3부 참고).

### 4.2 `by=` 세분화 시도 결과 — 버스/지하철 단독 필터는 불가능 (실기기+PC 테스트로 확정)

GoNow의 회원 이동수단 선호(`TransitType`: `ALL`/`SUBWAY`/`BUS`)를 딥링크에도 그대로 반영할 수 있을지 테스트함.

- **전제 확인**: 카카오맵 대중교통 검색 결과 화면은 "전체"(버스만/지하철만/버스+지하철 조합을 다 합친 것) / "버스" / "지하철" / "버스+지하철" 4개 탭으로 나뉨. `by=publictransit`로 열면 항상 "전체" 탭이 뜨는데, 이건 GoNow의 `ALL`(상관없음)과 개념적으로 대응됨.
- **`by=bus`, `by=subway` 같은 비공식 값을 직접 테스트**(`m.map.kakao.com/scheme/route`에 동일 좌표로 `by=publictransit`/`by=bus`/`by=subway` 세 가지를 PC에서 열어 비교) — **셋 다 완전히 동일한 결과("전체" 탭)로 렌더링됨.** 즉 이 URL Scheme은 대중교통 내에서 버스/지하철을 구분해서 여는 기능 자체가 없음(1.1의 공식 4개 값 — `car`/`publictransit`/`foot`/`bicycle` — 이 정말 전부라는 게 실측으로도 재확인됨).
- **결론**: 딥링크 테스트 화면의 이동수단 버튼은 대중교통(`publictransit`)/자동차(`car`) 2개로 유지. `SUBWAY`/`BUS`/`ALL` 세분화는 딥링크가 아니라 **ODsay 기반 실제 경로 계산(Flask) 쪽에서 이미 담당하고 있는 역할**이라, 딥링크 단계에서 굳이 재현할 필요가 없음(딥링크는 "계산 다 끝난 뒤 지도로 보조 확인용"으로만 열리는 것이라 그 시점엔 이동수단 세분화가 의미 없음).

### 4.3 경로 우선순위(최소시간/최소환승/최소도보)도 딥링크로 지정 불가 — 추론(미실측)

GoNow의 회원 경로 우선순위 선호(`PriorityType`: `MIN_TIME`/`MIN_TRANSFER`/`MIN_WALK`)도 딥링크에 반영 가능한지 확인.

- 1.1·1.2의 공식 파라미터는 `sp`/`ep`/`vp`(경유지)/`by`(이동수단)가 전부이고, 정렬·우선순위 관련 파라미터는 애초에 스펙에 없음.
- 4.2에서 스펙에 없는 값(`by=bus`/`by=subway`)이 실제로도 안 먹히는 게 실측으로 확인된 전례가 있어서, 같은 패턴으로 우선순위 파라미터도 지원 안 될 것으로 추정 — **다만 이번 건은 4.2와 달리 PC/실기기로 직접 재테스트하지는 않은, 스펙 기반 추론 단계.** 필요하면 나중에 실측으로 재확인.
- **결론(4.2와 동일한 논리)**: 설령 안 되더라도 문제 없음 — `PriorityType` 선호는 딥링크가 아니라 **ODsay 기반 실제 경로 계산(Flask)에서 이미 반영되고 있는 값**이고, 딥링크는 그 계산이 끝난 뒤 지도로 보조 확인하는 용도라 여기서까지 재현할 필요가 없음. (근거는 아래 4.4 — 코드로 실제 확인됨.)

### 4.4 (2026-08-07 정정) `TransitType`/`PriorityType` → ODsay 매핑, 실측 결과 대거 틀렸던 것으로 확인 — 실제 버그 3건 발견·수정

4.2·4.3의 "딥링크가 세분화 안 해줘도 상관없다, 이미 앞단(ODsay)에서 처리되고 있다"는 결론 자체는 여전히 유효하다. 하지만 그 근거로 삼았던 아래 표(구버전)는 **콘솔 공식 문서 + 실측으로 재검증한 결과 절반 이상 틀린 것으로 드러났다.** 이 표만 믿고 있었다면 `TransitType`/`PriorityType` 선호가 지금까지 조용히 무시되고 있었을 것 — 딥링크 작업 중 우연히 발견해서 바로잡음.

**(정정 전, 틀렸던 내용)**: `TransportMode` → ODsay `SearchType`(0/1/2), `PriorityType` → ODsay `OPT`(0/1/2)로 완전히 매핑된다고 서술했었음.

**(정정 후, 콘솔 공식 문서 + 실측 확인)**:

| GoNow 설정 | 실제 매핑돼야 할 ODsay 파라미터 | 값 |
|---|---|---|
| `TransportMode`(`ALL`/`SUBWAY`/`BUS`) | **`SearchPathType`**(`SearchType` 아님) | `ALL`=0, `SUBWAY`=1, `BUS`=2 |
| (신규 발견) 도시내/도시간 구분 | `SearchType`(0=도시내, 1=도시간) | GoNow는 이 값을 몰라서 계속 `SearchType`에 위 표의 이동수단 값을 잘못 넣고 있었음 |
| `PriorityType`(`MIN_TIME`/`MIN_TRANSFER`/`MIN_WALK`) | **ODsay `OPT`엔 이 개념 자체가 없음** — `OPT`은 `0`(추천경로)/`1`(타입별정렬) 두 값뿐, "최소환승"/"최소도보" 정렬 기준이 애초에 존재하지 않음 | — |

**실제로 발견·수정한 버그 3건 (`gonow-flask`, `transit_route.py`/`alarm.py`)**:

1. **`SearchType`/`SearchPathType` 혼용** — 지하철/버스 선택값을 엉뚱하게 `SearchType`(도시내/도시간 구분 파라미터)에 넣고 있었음. 실측 결과 `SearchType=1`은 ODsay가 아예 `error -99`(검색결과 없음)로 응답 → 코드의 기존 폴백 로직(그 모드로 결과 없으면 ALL 재시도)이 매번 조용히 발동 → **`SUBWAY`/`BUS` 선호가 지금까지 사실상 한 번도 반영된 적이 없었을 가능성이 높음.** `SearchType`은 `0` 고정, `SearchPathType`에 이동수단 값을 넣도록 수정.
2. **도시간(시외) 이동 미지원** — 위 버그를 고치며 `SearchType`을 `0`(도시내) 고정으로 바꾸면, 서울↔대전 같은 장거리 여정은 KTX/고속버스를 아예 검색 대상에서 빼고 시내버스만으로 억지로 경로를 짜맞춰 **4시간 넘는 비정상 경로**를 응답하는 새 문제가 실측으로 드러남(4.6절 참고). 두 지점 간 직선거리가 70km(수도권 광역 통근권 바깥 기준)를 넘으면 `SearchType=1`(도시간)로 자동 전환하도록 수정 — `optimizer.py`의 `haversine` 재사용.
3. **`OPT` 기반 우선순위가 애초에 존재하지 않는 개념이었음** — `MIN_TRANSFER`/`MIN_WALK`를 `OPT=1`/`OPT=2`로 보냈지만 ODsay `OPT`엔 그런 정렬 기준이 없어(0=추천/1=타입별정렬 뿐) 사실상 아무 효과가 없었을 것으로 추정. `OPT`은 `0`(추천경로) 고정으로 보내고, 대신 **Flask가 ODsay 응답 후보 리스트(보통 10~20개)를 직접 재정렬**하도록 수정: `MIN_TIME`→`info.totalTime`, `MIN_TRANSFER`→`busTransitCount+subwayTransitCount`, `MIN_WALK`→`info.totalWalk` 각각 최솟값 선택. 기존엔 `path = paths[0]`(ODsay의 "추천" 1위)을 무조건 썼는데, 실측상 이게 진짜 최단시간조차 보장 안 함(4.5절 참고)도 이번에 같이 확인·수정.

**결론**: 4.2·4.3의 "딥링크가 세분화 안 해줘도 상관없다"는 결론은 여전히 유효하다(선호 반영은 ODsay 쿼리 단계 담당이 맞음) — 다만 그 담당 파라미터가 이번 정정 전까지 실제로는 잘못 연결돼 있었다는 게 이번 딥링크 작업 중 부수적으로 드러난 별개의, 훨씬 심각한 기존 버그였다.

### 4.5 ODsay `OPT`(추천경로 vs 타입별정렬)의 실체 — 실측

콘솔 공식 문서: `OPT=0`="추천경로"(대표 후보 몇 개), `OPT=1`="타입별정렬"(지하철/버스/혼합 그룹화). "최소환승"/"최소도보" 같은 정렬 개념은 없음.

**"추천경로"가 실제로 뭘 최적화하는지 실측(신촌↔종로3가, 19개 후보 중 `totalTime` 동률 3개 비교)**:

| | totalTime | totalWalk | totalIntervalTime |
|---|---|---|---|
| ODsay 추천 1위(`paths[0]`) | 25분 | 517m | **11**(최소) |
| 후보 A | 25분 | 523m | 16 |
| 후보 B | 25분 | **499m**(최소) | 16 |

시간이 동률일 때 도보가 아니라 **배차간격(`totalIntervalTime`)이 가장 낮은 쪽을 우선**했다(도보 최소 후보는 따로 있었는데도 안 뽑음). 즉 "추천경로" ≈ 총 소요시간 최우선 → 동률/근소 차이면 배차간격 적은 쪽 → 도보량은 거의 안 봄, 으로 잠정 결론. 한 케이스 실측이라 확정은 아니지만, `paths[0]`을 무조건 신뢰하면 안 된다는 근거로는 충분함(2.4절의 Flask 자체 재정렬 결정 근거).

`OPT=2`(문서에 없는 값) 실측 결과는 `OPT=0`이 아니라 **`OPT=1`과 동일하게 동작**함 — "정의 안 된 값은 기본값(0)으로 처리될 것"이라는 예상과 다름. 딱 한 번 테스트한 결과라 재현성 확인은 안 했으나, `OPT`에 문서화 안 된 값을 보내는 시도 자체를 하지 않는 게 안전.

### 4.6 `SearchType`(도시내/도시간) 실측 — 서울↔대전

- **`SearchType=0`(도시내) 고정 상태로 서울↔대전(약 143km) 검색**: 에러 없이 "성공" 응답하지만, 지하철·시내버스망만으로 우회 경로를 억지로 짜맞춰 **250분(4시간 15분)**, 지하철 0회(`subwayCount:0`) 경로를 반환. KTX/고속버스는 검색 대상에서 아예 빠짐.
- **`SearchType=1`(도시간)**: KTX(45분, 19,900원)/무궁화호(93~104분, 15,200~16,300원)/고속버스(110~135분, 15,800~18,100원) 등 정상적인 시외 교통망 응답.
- **결론**: `SearchType=0` 고정은 장거리 여정에서 조용히 비정상 경로(에러 없이 "성공"으로 응답)를 만들어낸다 — 반드시 거리 기준 자동 분기가 필요함(4.4절 버그#2, 이미 수정 완료).

개발 중 ODsay 응답을 직접 조회하며 확인하고 싶을 땐 [odsay-mcp-guide.md](odsay-mcp-guide.md) 참고. ODsay를 TMAP/카카오 등 다른 provider와 계산 엔진 자체로 비교한 조사(이 문서의 관심사인 "딥링크 파라미터 매핑"과는 다른 각도)는 [transit-provider-research.md](transit-provider-research.md) 참고.
