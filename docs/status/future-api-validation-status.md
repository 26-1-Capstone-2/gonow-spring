# 버그40 실측 검증 진행 현황

카카오모빌리티 "미래 운행 정보 길찾기"(`/v1/future/directions`)를 자가용(DRIVING)
`departureAlarmTime` 계산에 2-pass로 도입하기 전, 먼 미래 리드타임(4~44시간)에서도
예측이 충분히 정확한지 실측 검증하는 작업의 진행 기록. BUGS.md 버그40 항목 참고.

지원 스크립트(`record.sh`/`verify.sh`/`future_api_validation.py`)와 원본 데이터 파일
(`future_api_results.json`)은 자동화를 그만두고 수동 검증으로 전환하면서 삭제됨 —
이 문서가 유일한 기록. 이후 검증은 `src/test/http/future_api.http`(이 저장소,
IntelliJ HTTP Client)를 직접 실행해서 수동으로 진행한다.

## STEP0 사전 점검 (통과)

근접 리드타임(3분 후) future vs realtime: 예측 1313초 vs 실제 1281초, 오차 **+2.5%**
— future API 자체의 기본 신뢰성 확인됨.

|---|---|---|---|---|---|---|---|---|

**STEP3/4/5는 1차 시도가 무효 처리되어 재측정 중**: 자동 체크 체인이 끊겨서 대조(realtime)
호출이 목표 시각보다 각각 1.5시간(STEP3)/2시간8분(STEP4)/8시간(STEP5) 늦게 실행됐고, 그
지연 때문에 측정된 "실제" 값이 원래 재려던 시각의 교통상황을 반영하지 못해 무효 처리함.
위 표의 목표 시각은 재기록된 새 시각(다음날 같은 시간대)이며, 예측값도 그 새 시각 기준으로
다시 받아온 값이다.

## 남은 검증 방법 (수동)

1. `src/test/http/future_api.http`를 IntelliJ에서 연다.
2. 각 시나리오의 목표 시각이 지난 뒤, 해당 번호의 **"-realtime"(대조) 요청만** 실행한다
   (예: STEP2 검증 시 "2-realtime"). "-future" 요청은 다시 실행할 필요 없음 — 위 표의
   예측값이 이미 확정된 값이다.
3. 응답의 `routes[0].summary.duration`을 위 표의 예측값과 비교해 오차%를 계산한다
   (`오차% = (예측 - 실제) / 실제 × 100`).
4. 6개 전부 나오면 이 표를 갱신하고, BUGS.md 버그40 항목에 최종 결론(2-pass 도입 여부,
   버그34 착수 여부)을 반영한다.

## 판단 기준 (참고)

- STEP1(근접)은 이미 오차가 매우 작음(+1.5%) — future API 자체의 기본 신뢰성은 확인된 상태.
- 핵심 질문은 **장시간 리드타임**(STEP2 20.5h, STEP6 44.5h)에서도 이 정확도가 유지되는가.
  여기서 오차가 크게 벌어지면 2-pass 도입 근거가 약해지고, 작게 유지되면 버그34(재계산
  트리거 추가)는 상대적으로 덜 중요해질 수 있음 — 상세 근거는 BUGS.md 버그34/40 항목의
  "OO와의 관계" 서술 참고.
