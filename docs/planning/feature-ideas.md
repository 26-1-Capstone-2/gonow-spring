# GoNow 기능 확장 아이디어 (2026 오픈소스 개발자대회 대비)

대회 참가 규정은 [oss-contest-2026.md](oss-contest-2026.md) 참고. 이 문서는 "무엇을 만들지"에 대한 검토용 아이디어 모음이며, 확정된 로드맵이 아니다 — 각 아이디어는 장단점을 함께 적어뒀으니 팀 논의로 취사선택할 것.

**전제**: 서비스 대상을 갤럭시(안드로이드) 사용자로 한정한다. iOS 지원을 하지 않으므로 아래 아이디어들에서 iOS 관련 제약(Apple Developer 계정 등)은 고려하지 않는다.

---

## 아이디어 A — 지도 연동 (외부 지도 앱 딥링크)

**현재 상태**: 프론트엔드 어디에도 실제 지도 렌더링이 없다. 장소 검색은 카카오 REST API(`src/api/kakao.ts`)로 좌표만 받아오는 텍스트 검색(`AddressSearchView.tsx`)뿐이고, 그룹 알람 대시보드(`ArrivalDashboardSheet.tsx`)도 참가자 위치를 텍스트/뱃지로만 보여준다.

**검토 경과 (원래 3가지 용도를 검토했으나 아래처럼 정리됨)**:
1. ~~장소 선택 화면에서 지도를 탭해서 고르기~~ — 텍스트 검색이 이미 잘 작동해서 우선순위 낮음, 보류.
2. **출발 후 목적지까지 길찾기** — 채택. 카카오맵/티맵 같은 기존 내비게이션 앱이 이미 완성도 높게 잘하는 영역이라 우리가 직접 지도를 그려서 재구현할 이유가 없다. "출발 알람이 울리면 목적지까지 카카오맵 길찾기가 원터치로 열리는 버튼"이면 충분 — `Linking.openURL()`로 카카오맵 딥링크 스킴 하나 호출하는 수준이라 구현이 매우 간단하다.
3. ~~그룹 대시보드에 참가자 실시간 위치 표시~~ — **제외**. 사용자가 실제로 궁금한 건 "친구가 지금 어느 좌표에 있는지"가 아니라 "몇 시쯤 오는지"라는 실행 가능한(actionable) 정보이고, 이건 이미 텍스트 대시보드가 제공하고 있다. 실시간 위치를 계속 노출하는 데 대한 프라이버시 부담과, 여러 참가자 좌표를 갱신·표시하는 구현/서버 비용을 고려하면 얻는 가치가 크지 않다고 판단.

**결론 — 자체 지도 SDK 임베드는 불필요, 그러나 가치는 작지 않음**: "지도 SDK 임베드"(카카오맵/MapLibre 같은 지도 그리기 부품을 앱 화면 안에 직접 심어서, 우리 서버 데이터를 지도 위에 자유롭게 얹는 방식)가 필요했던 이유는 사실상 3번(참가자 위치 표시) 하나뿐이었다. 그 용도가 빠지면서, 남은 2번은 "카카오맵 앱으로 화면을 통째로 넘겨버리는" **딥링크**만으로 충분해진다 — 구현도 `Linking.openURL()` 한 줄 수준으로 가볍다. 구현이 작아졌다고 실사용 가치까지 작은 건 아니다 — 경로를 모르는 사용자의 재검색 마찰을 없애주고, 알림이 실수로 지워져도 앱 안 어디선가는 항상 접근 가능해야 한다는 게 핵심 요구사항이다. (참고: 나중에 참가자 위치 표시를 다시 고려하게 되면 그때 카카오맵 SDK vs MapLibre 같은 SDK 임베드 옵션 비교가 다시 필요해짐.)

**언제·어디에 노출할지, 목적지를 어떻게 잡을지, 카카오맵 공식 스펙, 실기기 검증 결과** — 전부 [kakao-map-deeplink-spec.md](../reference/kakao-map-deeplink-spec.md)에 구현 가이드로 정리해뒀다. 실기기 테스트로 카카오맵 앱 설치/미설치 양쪽 다 검증 완료된 상태.

## 아이디어 B — 외부 캘린더 연동

**현재 상태**: `MainCalendarScreen.tsx`/`YearCalendarScreen.tsx`는 완전히 자체 제작된 UI로, 공공데이터 공휴일 API + GoNow 자체 알람 데이터만 보여준다. `expo-calendar`, Google Calendar, ICS 관련 코드는 전혀 없다.

**제안**: 풀 Google Calendar OAuth 연동(동의화면 등록, 토큰 갱신 관리 등)은 복잡도가 꽤 높다. MVP로는 **`expo-calendar`(기기 캘린더) 연동을 우선 제안** — 안드로이드 기기의 캘린더는 보통 이미 Google 계정과 동기화돼 있어서, OAuth 없이도 "구글 캘린더에 뜨는" 효과를 낼 수 있다.
- 기본: GoNow 알람(개인/귀가/그룹) 생성 시 기기 캘린더에 일정 자동 등록
- 스트레치: 기기 캘린더의 기존 일정을 읽어서 "내일 오후 3시 미팅이 있는데, 여기까지 가는 알람을 만들까요?" 같은 역방향 제안 — 구현 난이도는 높지만 차별화 포인트로는 강력함

## 아이디어 C — 실제 지오펜싱 도입

**현재 상태**: OS 지오펜싱 API(`Location.startGeofencingAsync`)는 쓰지 않는다. `docs/spec/journey-state-machine.md`에 "GPS는 지오펜싱 대신 주기적 폴링 방식을 사용한다"고 명시돼 있고, 그 이유가 "iOS 개발 시 Apple Developer 계정 없이 지오펜싱 불가"였다. **서비스를 갤럭시(안드로이드) 전용으로 한정하면 이 제약 자체가 사라지므로**, 부담 없이 재검토할 수 있다.

**2026-08-11 — 착수 방향 구체화됨**: 버그3(백그라운드 GPS interval 고정) 수정 작업 중, "백그라운드에만 있으면 폴링 주기가 실시간으로 안 좁혀지는" 근본 한계를 완전히 해결하려면 위험한 코드(백그라운드에서 위치추적 서비스 재시작 — 과거 실제 크래시 전례 있음)가 필요하다는 걸 확인했다. READY/DEPARTING/NEARDEST는 애초에 폴링이 아니라 "경계 진입/이탈 감지"만 필요한 상태라 지오펜싱으로 바꾸면 이 문제 자체가 사라진다는 결론에 도달, 하이브리드가 아니라 **이 세 상태는 지오펜싱으로 완전히 대체, MOVING만 기존 폴링 유지**하는 방향으로 구체화됨. 상세 설계·앵커 확정 문제·기존 버그(버그41/29/34)와의 상호작용·구현 순서는 [geofencing-migration-plan.md](geofencing-migration-plan.md) 참고.

## 아이디어 D — 조사 중 발견한 UX 갭 ("정말 편리한지"에 대한 답)

사용자가 물은 "알람만 울려주면 지각하지 않고 잘 찾아갈 수 있을지"에 대한 검토 결과, 코드 조사 과정에서 눈에 띈 갭들:

- **출발 알람 이후 "안내 공백"**: 알람이 울린 후엔 사용자가 별도 지도 앱(카카오맵/네이버맵/구글맵)으로 갈아타야 한다. GoNow의 역할이 "출발하라고 알려주는 것"에서 끝나고, "잘 찾아가고 있는지"는 챙겨주지 않는다 → 아이디어 A(지도 딥링크)가 이 공백을 메울 수 있음.
- **"지각 위험" 사후 재알림이 없음**: 현재 상태머신(`journey-state-machine.md`)은 목적지까지의 근접도(NEARDEST/ARRIVED)만 보고 판단한다. 출발 후 버스를 놓치거나 정체가 생겨서 ETA가 나빠져도 재경고가 없다. "지금 속도면 5분 늦을 수 있어요" 같은 사후 알림을 추가하면 실사용 가치가 클 것 — 구현 자체도 상태머신에 한 단계(ETA 재계산 후 target_time 초과 예상 시 알림) 추가하는 정도라 비교적 가볍다.
- **그룹 알람에서 "친구가 어디쯤 오고 있는지" 궁금한 니즈**: 검토는 했으나(아이디어 A 참고), 실제로 필요한 건 좌표가 아니라 "몇 시쯤 오는지"라는 시간 정보라고 판단해 지도 표시 대신 기존 텍스트 대시보드로 충분하다고 결론 — 대신 D의 사후 지각 재알림이 이 니즈를 시간 축에서 더 정확하게 채워줄 수 있음.
- **출발 시각 산정 근거의 투명성 부족**: 사용자가 "왜 하필 이 시각에 출발하라는 거지?"를 납득하기 어려움. 경로를 카카오맵 딥링크로 미리 보여주는 정도로도 어느 정도 신뢰도 개선에 도움될 수 있음.

## 아이디어 E — 날씨 연동 소요시간 보정

**현재 상태**: 출발 알람 계산은 대중교통 시간표/실시간 교통정보만 반영하고, 날씨는 전혀 고려하지 않는다. 비/눈이 오면 도보 이동이 느려지고 대중교통도 지연되기 쉬운데 지금은 그걸 감안 안 해준다.

**제안**: 기상청 공공 API(무료)로 강수/적설 예보를 조회해서, 우천·강설 시 여유시간(`preparationTime`)에 보정계수를 적용 — 예를 들어 비 예보면 출발 여유시간을 몇 분 더 넉넉하게 잡아주는 식. 외부 API 하나 추가 + 기존 계산식에 보정 로직을 얹는 정도라 구현 부담이 낮은 편이고, "비 오는 날 우산 챙기다 늦었다" 같은 실제 불편을 직접 해결해줘서 체감 가치가 크다.

## 아이디어 F — 지속 알림(Ongoing Notification) 카운트다운

**현재 상태**: 단계별 출발 알람은 특정 시점에 한 번씩 울리는 방식이고, 알림바에 "출발까지 몇 분 남았는지"가 상시로 떠 있지는 않다.

**제안**: notifee 인프라가 이미 갖춰져 있으니, 이를 확장해서 알림바에 "출발까지 12분" 같은 카운트다운을 지속적으로 띄워주는 Ongoing Notification을 추가. 사용자가 앱을 열지 않아도 알림바만 슬쩍 봐도 상태를 바로 파악할 수 있어 체감 편의성이 좋다. 기존 알림 채널/발송 로직을 재사용할 수 있어 신규 인프라 구축 부담이 상대적으로 적다.

## 아이디어 G — TTS 음성 브리핑

**현재 상태**: 모든 안내가 텍스트/알림 형태이고 음성 안내는 없다.

**제안**: 안드로이드 기본 TTS API로 "지금 나가야 안 늦어요, OO역까지 도보 5분" 같은 음성 브리핑을 제공. 구현 자체는 안드로이드 기본 API라 부담이 크지 않고, 시각장애인·고령자 등 접근성을 배려하는 기능이라 "오픈소스 개발자대회"에서 사회적 가치를 어필하는 포인트로도 잘 맞는다.

## 우선순위/난이도 참고

가성비만 보면 **D와 A를 함께 먼저 처리하는 걸 추천**한다. 둘 다 새 라이브러리·OAuth·네이티브 리빌드가 거의 필요 없어서 비용이 매우 낮은데(A는 딥링크 버튼 하나, D는 상태머신에 로직 추가), 앱의 핵심 가치("안 늦게 해준다", "잘 찾아가게 해준다")와 바로 연결돼서 비용 대비 효과가 가장 좋다 — 특히 A는 구현이 작아졌다고 실사용 가치까지 작은 게 아니라는 점에 유의(위 본문 참고). B·C는 시간이 남으면 검토.

| 아이디어 | 실사용 가치 | 구현 난이도 | 비고 |
|---|---|---|---|
| A. 지도 연동 (딥링크) | 높음 | 매우 낮음 | 경로 모르는 사용자의 재검색 마찰 제거 + 알림 삭제에 대비한 앱 내 상시 노출까지 포함해야 실효성이 제대로 산다 — **가성비 최상위(D와 공동)** |
| B. 외부 캘린더 연동 (기기 캘린더 기준) | 중간 | 낮음 | Google OAuth 없이 `expo-calendar`로 시작하면 상대적으로 가벼움 |
| C. 지오펜싱 도입 | 중간(기술적 차별점은 큼) | 중간~높음 | 안드로이드 한정이라 iOS 제약 없이 바로 검토 가능. 다만 백엔드 최적화라 데모에서 눈에 잘 안 띔 |
| D. 사후 지각 재알림 | 높음 | 낮음 | "안 늦게 해준다"는 핵심 가치에 직결, 상태머신에 한 단계 추가하는 수준 — **가성비 최상위(A와 공동)** |
| E. 날씨 연동 보정 | 중간 | 낮음 | 외부 API 1개 + 보정 로직, 실사용 체감 가치 높음 |
| F. 지속 알림 카운트다운 | 중간 | 낮음~중간 | 기존 notifee 인프라 재사용 가능 |
| G. TTS 음성 브리핑 | 중간(접근성 어필 강함) | 낮음 | 안드로이드 기본 API, 사회적 가치 스토리텔링에 유리 |

## 대회 규정과의 연결

- [oss-contest-2026.md](oss-contest-2026.md)의 AI 모델 활용 규정(오픈웨이트/MCP 권장, 폐쇄 API 단순 연결 제한)은 이 문서의 아이디어들(지도/캘린더/지오펜싱/UX)과는 별개 주제다 — AI 기능을 추가로 고려한다면 그 규정을 따로 검토해야 함(이번 문서 범위에서는 다루지 않음).
- (참고) 애초에 지도 SDK 라이브러리 선택 자체가 규정상 제약이 아니라는 점은 확인했으나, 아이디어 A가 딥링크로 축소되면서 지금은 라이브러리 선택 자체가 필요 없어졌다 — 참가자 위치 표시 용도를 나중에 다시 채택할 경우에만 다시 관련성이 생긴다.
