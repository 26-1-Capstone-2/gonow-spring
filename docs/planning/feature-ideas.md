# GoNow 기능 확장 아이디어 (2026 오픈소스 개발자대회 대비)

대회 참가 규정은 [oss-contest-2026.md](oss-contest-2026.md) 참고. 이 문서는 "무엇을 만들지"에 대한 검토용 아이디어 모음이며, 확정된 로드맵이 아니다 — 각 아이디어는 장단점을 함께 적어뒀으니 팀 논의로 취사선택할 것. 이미 채택되어 구현이 끝난 아이디어(지도 딥링크, 지오펜싱 등)나 논의 끝에 필요 없다고 정리된 아이디어(캘린더 연동, 날씨 연동, TTS 음성 브리핑)는 이 문서에서 제외했다 — 구현 완료분은 `CLAUDE.md`/`docs/history/geofencing-migration-plan.md`/`docs/reference/kakao-map-deeplink-spec.md`에서 확인 가능.

**전제**: 서비스 대상을 갤럭시(안드로이드) 사용자로 한정한다. iOS 지원을 하지 않으므로 아래 아이디어들에서 iOS 관련 제약(Apple Developer 계정 등)은 고려하지 않는다.

## 아이디어 D — 사후 지각 재알림

사용자가 물은 "알람만 울려주면 지각하지 않고 잘 찾아갈 수 있을지"에 대한 검토 결과, 코드 조사 과정에서 눈에 띈 갭들:

- **"지각 위험" 사후 재알림이 없음**: 현재 상태머신(`journey-state-machine.md`)은 목적지까지의 근접도(NEARDEST/ARRIVED)만 보고 판단한다. 출발 후 버스를 놓치거나 정체가 생겨서 ETA가 나빠져도 재경고가 없다. "지금 속도면 5분 늦을 수 있어요" 같은 사후 알림을 추가하면 실사용 가치가 클 것 — 구현 자체도 상태머신에 한 단계(ETA 재계산 후 target_time 초과 예상 시 알림) 추가하는 정도라 비교적 가볍다.
- **그룹 알람에서 "친구가 어디쯤 오고 있는지" 궁금한 니즈**: 검토했으나, 실제로 필요한 건 좌표가 아니라 "몇 시쯤 오는지"라는 시간 정보라고 판단해 지도 표시 대신 기존 텍스트 대시보드로 충분하다고 결론 — 대신 위 사후 지각 재알림이 이 니즈를 시간 축에서 더 정확하게 채워줄 수 있음.
- **출발 시각 산정 근거의 투명성 부족**: 사용자가 "왜 하필 이 시각에 출발하라는 거지?"를 납득하기 어려움. 카카오맵 딥링크(이미 구현됨)로 경로를 미리 열어볼 수 있어 어느 정도 신뢰도 개선엔 도움되지만, 계산 근거 자체를 보여주는 건 아니라 근본적 해법은 아님.

## 아이디어 F — 지속 알림(Ongoing Notification) 카운트다운

**현재 상태**: 단계별 출발 알람은 특정 시점에 한 번씩 울리는 방식이고, 알림바에 "출발까지 몇 분 남았는지"가 상시로 떠 있지는 않다.

**제안**: 알림바에 "출발까지 12분" 같은 카운트다운을 지속적으로 띄워주는 Ongoing Notification을 추가. 사용자가 앱을 열지 않아도 알림바만 슬쩍 봐도 상태를 바로 파악할 수 있어 체감 편의성이 좋다.

**구현 시 확인/고려해야 할 점 (착수 전 재검토 결과 — 처음 생각보다 손이 더 감)**:
- 지금 상시 떠 있는 FGS 상단바 알림(`ForegroundService.start('GoNow 알람 실행 중', '출발 시간을 모니터링하고 있어요.')`, `backgroundLocationTask.ts:485`)은 notifee가 아니라 별도의 `ForegroundService` 네이티브 모듈을 쓰고, 지금은 고정 문구다 — 이 모듈이 실행 중 알림 텍스트를 갱신하는 API를 지원하는지부터 확인 필요(지원 안 하면 새 알림 채널/모듈이 따로 필요해져 범위가 커짐).
- GPS 폴링 interval이 적응형(상황에 따라 약 30초~5분)이라, 카운트다운을 매끄럽게(1분 단위 등) 갱신하긴 어렵고 "폴링될 때마다 남은 시간 갱신" 정도의 근사치가 현실적이다.
- FGS 알림은 추적 중인 알람 종류·개수와 무관하게 항상 하나의 인스턴스로 떠 있다("알람이 하나라도 있으면 FGS 유지" 정책, `docs/history/geofencing-migration-plan.md` 참고) — 개인/귀가/그룹 알람이 동시에 여러 개 추적 중이면 이 알림 하나에 어떤 알람의 카운트다운을 보여줄지 정책이 별도로 필요하다(가장 임박한 것 하나만? 여러 줄로 나열?).

**유용성 평가**: 이미 단계별 로컬 알림(1~4단계)이 시간 맞춰 울려주므로 "안심하려고 상시 확인하고 싶은" 소수 사용자에게는 유용하지만, 없어도 핵심 기능(지각 방지)엔 지장이 없는 부가 기능에 가깝다.

## 아이디어 H — 막차 모드 생성 시점 UX 개선 (새벽 01~04시 차단 메시지 고도화)

**현재 상태**: `JourneyService.validateLastTrainNotAlreadyMissed()`(`domain/journey/service/JourneyService.java:179-185`)는 막차 모드 귀가 여정을 오늘 날짜(`plan_date`)로 생성하려는 시도가 새벽 01시~`day-boundary-hour`(기본 4시) 사이면 "오늘 밤 막차는 이미 지났습니다"라는 400 에러로 무조건 차단한다.

**제안**: 이 시간대에 단순 차단 메시지만 보여주는 대신, "내일(다음 서비스데이) 막차로 대신 만들어드릴까요?" 확인 모달을 띄우고 승낙 시 `plan_date`를 +1일 해서 동일 생성 요청을 재전송하는 방식으로 개선. 이 시점엔 애초에 출발지 GPS가 없어 플라스크 실제 막차 검색 자체가 불가능하므로(CLAUDE.md "출발지 선택 정책" 참고), "다음날 막차를 찾아준다"는 게 새로운 계산이 아니라 단순히 `plan_date`를 하루 미뤄서 같은 생성 요청을 다시 보내는 것뿐 — 백엔드 변경 거의 없이 프론트에 확인 모달 하나만 추가하면 됨.

**배경(왜 필요한지)**: `plan_date`는 실질적으로 "도착 날짜"를 의미하는데(막차 모드에서 `target_time` = 귀가 도착 시각), 새벽 시간대에 "오늘"을 골라 만들려는 사용자는 대부분 이미 지나간 어젯밤 막차가 아니라 "오늘 밤 탈 막차"(도착은 내일 새벽, 즉 `plan_date`가 +1이어야 하는 경우)를 의도했을 가능성이 높다 — 날짜 선택 UI의 "오늘/내일" 감각과 `plan_date`의 실제 "도착일" 의미가 사용자 머릿속에서 어긋나기 쉬운 지점이라, 그냥 막기만 하면 사용자가 왜 막혔고 어떻게 다시 만들어야 하는지 스스로 알아내야 한다.

**검토했다가 기각한 대안**:
- 조용히 다음날로 자동 생성 — 사용자가 명시한 날짜와 다른 알람이 조용히 만들어지는 것은 "믿고 맡기는 지각 방지 서비스"에서 피해야 할 동작 변경이라 기각.
- 현행 유지(차단만) — 틀린 동작은 아니지만 사용자가 재시도 방법을 스스로 알아내야 하는 불친절함이 남음.

**진행 상태**: 아이디어 단계, 미착수. `BUGS.md`의 버그22(플라스크 런타임 계산 오류)·버그25(`/location` 4xx 무알림) 논의 중 파생된 아이디어지만, 그 버그들과는 독립적인 별도 UX 개선 건 — 이미 정상 동작하는 코드에 대한 편의성 개선이라 버그가 아님(`BUGS.md` 버그47).

## 아이디어 I — 그룹 초대 링크, 앱 미설치 유저용 플레이스토어 폴백

**현재 상태**: `docs/spec/group-invite-applinks.md`에 정리된 그룹 초대 유니버설 링크(`https://gonow-api.uk/join?code=...`)는 "앱이 이미 설치된 유저"만 대상으로 구현됐다. 앱이 없는 유저가 링크를 누르면 스프링이 서빙하는 초대 카드 페이지(`join.html`)만 보이고, 거기서 더 진행할 방법이 없다.

**제안**: `join.html`에 "설치 안 되어 있으면" 분기를 추가해 플레이스토어로 유도하는 버튼/자동 이동을 넣는다. 더 나아가 안드로이드 Play Install Referrer API를 붙이면, 설치 직후 앱을 처음 열 때 아까 누른 초대코드를 자동으로 복원(Deferred Deep Link)할 수 있어 "설치 → 코드 재입력" 단계를 없앨 수 있다.

**왜 지금 안 하는지**: 처음 이 기능을 설계할 때부터 "설치된 유저만 우선 신경 쓰자"고 범위를 명시적으로 좁혔다(도메인/호스팅 인프라를 새로 마련하는 부담을 피하려던 결정). 미설치 유저 대응은 실제로 앱이 어느 정도 사용자 기반을 갖춘 뒤에 우선순위를 다시 매기는 게 합리적 — Deferred Deep Link까지 포함하면 별도 안드로이드 네이티브 작업(Play Install Referrer 연동)이 필요해 구현 난이도도 낮지 않다.

## 아이디어 J — 막차 시각 하루 종일 미확정 시 넛지 알림

**현재 상태**: 버그41 수정(`docs/history/resolved-bugs.md` 참고) 이후, 막차 모드 귀가 여정은 사용자가 목적지(집) 700m 밖으로 한 번도 안 나가는 한 `target_time`이 계속 미확정 상태로 남는다 — 값을 지어내지 않는 정직한 동작이지만, 극단적으로 하루 종일 집 근처(재택 등)에만 머무르면 그날 밤 막차 계산이 끝내 이루어지지 않아 알람이 조용히 안 울린다. 다음날 정상적으로 외출하면 자동으로 회복되므로 영구 고장은 아니다.

**제안**: 밤 늦은 시각(예: 23시)까지 `target_time`이 여전히 `null`인 당일 막차 모드 여정을 찾아 FCM으로 "아직 오늘 막차 계산이 안 됐어요, 앱을 열어 확인해주세요" 같은 넛지 알림을 1회 발송. 기존 매분 스케줄러(`ArrivedTransitionScheduler`류)와 FCM Data 발송 인프라를 그대로 재사용 가능해 구현 자체는 작다.

**왜 지금 안 하는지**: 발생 조건이 "막차 모드 + 그날 하루 종일 700m 밖을 한 번도 안 나감"이라는 꽤 좁은 조합이라 우선순위가 낮다고 판단, 문서화만 해두고 보류하기로 함.

**진행 상태**: 아이디어 단계, 미착수. 버그41 수정(2026-08-20) 중 발견된 잔여 한계 — 버그는 아님(정보가 없으면 정직하게 "모름"을 반환하는 게 올바른 동작이라, 버그41의 해결 범위로는 보지 않기로 함).

## 우선순위/난이도 참고

**D(사후 지각 재알림)를 우선 추천**한다 — 새 라이브러리·OAuth·네이티브 리빌드 없이 상태머신에 로직을 추가하는 수준인데도 앱의 핵심 가치("안 늦게 해준다")와 바로 연결된다. F·H는 실사용 가치 대비 구현 난이도가 상대적으로 낮은 우선순위.

| 아이디어 | 실사용 가치 | 구현 난이도 | 비고 |
|---|---|---|---|
| D. 사후 지각 재알림 | 높음 | 낮음 | "안 늦게 해준다"는 핵심 가치에 직결, 상태머신에 한 단계 추가하는 수준 — **가성비 최상위** |
| F. 지속 알림 카운트다운 | 중간 | 중간 | 재검토 결과 FGS 모듈 동적 갱신 API 확인·적응형 폴링 주기와의 정합·다중 알람 표시 정책까지 필요해 처음 예상보다 손이 감 |
| H. 막차 생성 시점 UX 개선 | 낮음~중간(편의성) | 매우 낮음 | 이미 정상 동작하는 코드의 문구/플로우 개선, 백엔드 변경 거의 없음 |
| I. 초대 링크 미설치 유저 폴백 | 낮음~중간 | 중간 | 스토어 유도만이면 쉬움, Deferred Deep Link까지 하면 네이티브 작업 필요 |
| J. 막차 미확정 넛지 알림 | 낮음(좁은 재현 조건) | 낮음 | 기존 스케줄러/FCM 인프라 재사용, 발생 조건이 좁아 후순위 |
