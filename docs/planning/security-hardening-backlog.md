# 운영 환경 보안 강화 백로그

지금 당장 고치지 않지만, 배포/운영 관점에서 시간이 남을 때 검토할 만한 보안 설정 개선 아이디어를 모아두는 곳. 기능 동작에는 문제없어서 `BUGS.md`(활성 버그 트래커)가 아니라 여기에 기록한다.

---

## 1. 운영(prod) 환경에서 Swagger UI 비활성화 검토

**발견 경위**: 2026-08-19, 그룹 초대 유니버설 링크(`/join`) 작업 중 `SecurityConfig`의 permitAll 목록(`/docs`, `/docs/**`, `/swagger-ui/**`, `/v3/api-docs/**`)을 다시 보다가 논의됨.

**내용**: 지금은 개발 편의를 위해 Swagger UI가 인증 없이 누구에게나 열려 있다. GoNow API는 서드파티 개발자가 붙는 공개 API가 아니라 자체 앱 전용이라, 일반 대중이 이 문서를 볼 합당한 이유가 없다. 실제 데이터 접근은 여전히 JWT가 필요해서 즉각적인 취약점은 아니지만, 전체 엔드포인트/요청·응답 필드/검증 규칙을 그대로 노출해 공격자의 정찰 비용을 낮춘다. 현업에서는 보통 dev/staging엔 열어두고 prod에서는 끄거나 최소한 접근 제한(Basic Auth, IP 제한 등)을 건다.

**왜 지금 안 고치는지**: `application.yml`이 프로필 분리 없이 단일 설정으로 되어 있어(`flask.url`이 로컬 테스트 때마다 수동으로 바꿔야 하는 것과 같은 이유), "prod에서만 끄기"를 하려면 프로필 분리 작업이 먼저 필요하다. 학생 프로젝트/오픈소스 대회 출품작 특성상 심사자가 API 구조를 살펴보는 데 지금 상태가 오히려 도움이 될 수도 있어 우선순위가 낮음.

**착수 시 방향**: `spring.config.activate.on-profile`로 `application-prod.yml` 분리 후, `springdoc.api-docs.enabled=false` / `springdoc.swagger-ui.enabled=false`를 prod 프로필에서만 적용하거나, `SecurityConfig`에서 프로필별로 permitAll 목록을 분기.

## 2. 프론트(`GoNow_Fronted`) npm 의존성 취약점 39건 — Expo SDK 메이저 업그레이드 필요

**발견 경위**: 2026-08-19, GitHub Dependabot 알림 확인 중 `npm audit` 결과 34~39건(치명적 1, 높음 18, 보통 15) 확인.

**내용**: 취약점 전부가 `@expo/cli`/Metro 번들러/`postcss`/`js-yaml`/`tar` 등 **빌드 타임 도구 체인 하나**에서 흘러나온다 — 앱이 실제 사용자 폰에서 실행될 때 포함되는 코드가 아니라 개발자 PC/CI에서만 도는 도구들이고, 유형도 대부분 악의적 입력에 의한 DoS(무한루프/메모리 폭증)라 GoNow 사용자를 직접 노릴 수 있는 경로는 아니다. 다만 `expo` 패키지 자체도 이 체인에 얽혀 "취약함"으로 표시된다.

**`--force` 없는 `npm audit fix`는 무의미함(직접 테스트 확인)**: `--dry-run`으로 확인한 결과, force 없이 돌리면 60개 패키지가 바뀌면서도(`peer dependency` 경고 다수 발생) 취약점은 34건 그대로 남는다 — 전부 `expo@57.0.14`로의 **메이저 업그레이드**(`isSemVerMajor: true`)가 있어야만 해소되는 구조라, 어중간하게 실행하면 득 없이 위험만 진다.

**왜 지금 안 고치는지 / 왜 위험한지**: 이 프로젝트는 커스텀 네이티브 모듈(`modules/foreground-service`)과 `expo-location`/`expo-task-manager` 기반 지오펜싱·백그라운드 GPS 폴링, `expo-updates`(OTA 배포 메커니즘 자체)에 깊이 의존한다 — 전부 Expo SDK 메이저 버전 사이에서 실제로 API가 바뀐 이력이 있는 영역이자, 이번에 가장 공들여 고친 부분들과 정확히 겹친다. New Architecture(Fabric)가 최신 Expo SDK에서 기본값으로 강제될 가능성도 있어 커스텀 네이티브 모듈 호환성 리스크가 크다. 순수 비즈니스 로직/API 통신(`fetch` 기반)은 상대적으로 영향이 적을 것으로 예상되지만, 네이티브/백그라운드 스택은 업그레이드 자체보다 회귀 테스트 비용이 훨씬 크다.

**착수 시 방향**: 별도 브랜치/워크트리에서 진행, 네이티브 재빌드 후 GPS 폴링 시작/중지·지오펜스 등록/해제·백그라운드 태스크 발화·FCM 수신·단계별 로컬 알람·FGS 생명주기를 실기기로 전부 재검증한 뒤에만 병합. 급하게 처리할 작업이 아니라 시간 여유 있을 때 계획적으로 진행.
