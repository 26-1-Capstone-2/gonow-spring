# sync-docs — 문서-코드 및 문서 간 정합성 점검

## 왜 이 스킬이 필요한가

이 프로젝트는 코드 구조/DB 스키마/API 명세/상태 전이 로직을 `CLAUDE.md`와 `docs/` 아래 여러 문서에 상세히 적어둔다. 코드는 계속 바뀌는데 문서는 손으로 따라가야 해서, 시간이 지나면 문서가 실제 구현과 어긋나는 게 당연히 생긴다(오탈자, 새로 추가된 필드 누락, 이미 끝난 일을 "미구현"이라고 잘못 표시해둔 것 등). 문서 수가 여러 개로 늘어나면 문서끼리도 서로 다른 얘기를 하게 될 수 있다(같은 내용을 CLAUDE.md와 docs/spec/*가 다르게 서술하는 경우 등). 이 스킬은 그 드리프트(코드-문서 간, 문서-문서 간)를 찾아서 고치는 절차를 매번 처음부터 설명하지 않고 재사용할 수 있게 담아둔 것이다.

**이 스킬은 문서만 고친다.** 조사하다가 코드 자체가 이상해 보여도(버그로 의심되는 로직 등) 코드는 건드리지 말고 발견 사항으로만 보고한다. 문서를 코드에 맞추는 작업이지, 코드를 검토하는 작업이 아니다.

## 실행 전에 확인할 것

이 스킬은 서브에이전트를 여러 개 병렬로 띄우는, 시간(1~2분)과 비용이 드는 작업이다. 그래서:
- 사용자가 명시적으로 이 스킬을 요청했거나, 방금 도메인 로직을 크게 고친 뒤 먼저 "지금 문서 동기화 점검을 돌려볼까요?"라고 제안해서 동의를 받은 경우에만 실행한다.
- 판단만으로 조용히 자동 실행하지 않는다.

## 절차

### 1. 현재 문서 목록 파악

`docs/README.md`를 읽어서 지금 존재하는 참고 문서와 경로를 확인한다. 문서는 추가/삭제/이름 변경이 있을 수 있으므로 목록을 하드코딩하지 말고 매번 실제로 읽어서 파악한다.

### 2. 최근 변경 파악

`git log --oneline -20` 정도로 최근 커밋을 훑어서 최근에 어떤 영역이 바뀌었는지 감을 잡는다. 문서 드리프트는 "최근에 코드는 바뀌었는데 문서는 안 바뀐" 곳에서 제일 많이 생기므로, 최근 커밋과 관련된 영역을 우선순위로 조사하도록 아래 서브에이전트들에게 지시한다.

### 3. 조사 서브에이전트 4개를 병렬로 실행

Explore(또는 general-purpose) 서브에이전트를 **한 메시지에서 병렬로** 4개 띄운다. 각 에이전트에게는 반드시 다음을 지시할 것:
- 검증 대상 문서 경로와 대조할 코드 영역(또는 다른 문서)
- 최근 커밋과 관련된 부분을 우선 확인
- **보고 형식**: "불일치가 있는 것만" 문서 주장 vs 실제 코드/다른 문서(파일:줄번호 포함)로 구체적으로 보고하고, 일치하는 항목은 개수만 짧게 언급. 일치 목록을 장황하게 나열하지 않게 할 것 — 그래야 종합할 때 신호 대 잡음비가 높다.
- 파일 수정 금지, 읽기 전용 조사임을 명시

**에이전트 A — DB/엔티티/Enum/Repository (문서 vs 코드)**
`docs/spec/db-schema.md`의 테이블 정의, `CLAUDE.md`의 "Enum 상수 목록"·"~Repository 조회 메서드" 섹션을 실제 `domain/*/entity`, `domain/*/constant`, `domain/*/repository` 코드와 대조.

**에이전트 B — API 엔드포인트/DTO (문서 vs 코드)**
`CLAUDE.md`의 "현재 구현된 API 엔드포인트" 표(경로/인증/설명, 응답 필드 언급)를 실제 `domain/*/controller`, `domain/*/dto` 코드와 대조. 최근 커밋으로 추가/변경된 필드(예: 새 DTO 필드, 응답 구조 변경)가 표에 반영됐는지 특히 신경 써서 확인.

**에이전트 C — 상태머신/스케줄러/FCM (문서 vs 코드)**
`docs/spec/journey-state-machine.md`와 `CLAUDE.md`의 알람 메커니즘·스케줄러·FCM 관련 서술을 실제 `*Service`(상태 전이 로직), `global/scheduler/*`, `global/fcm/*` 코드와 대조. 특히 스케줄러가 문서에 적힌 것 "외에" 추가로 하는 일이 있는지(문서에 아예 없는 기능) 확인 — 존재하는데 문서에 없는 기능이 값보다 오탈자보다 더 중요한 발견이다.

**에이전트 D — 문서 간 상호 정합성 (md vs md, 코드 조회 없음)**
`docs/README.md`로 파악한 문서 전체를 서로 대조한다. 확인 포인트:
- 같은 사실을 두 문서가 다르게 서술하는 곳이 있는지 (예: `CLAUDE.md`의 요약과 `docs/spec/*`의 상세 설명이 실제로 같은 내용을 가리키는지, 값이나 조건이 어긋나지는 않는지)
- `CLAUDE.md`의 "구현 현황 > 완료/미구현" 목록이 `docs/status/*`, `docs/history/*`에 기록된 실제 완료/테스트 상태와 모순되지 않는지
- `docs/README.md` 색인에 적힌 경로가 실제 파일 위치와 일치하는지, 색인에 없는 문서가 새로 생기지 않았는지
- `docs/history/*`(과거 기록)에 있는 내용이 마치 현재도 유효한 것처럼 다른 문서에서 인용되고 있지는 않은지 (과거-현재 혼동)
이 에이전트는 코드를 읽을 필요 없이 문서들끼리만 비교하면 된다.

이 4갈래 분류는 이 저장소 구조(도메인/글로벌 패키지 + docs 폴더 구조)에 맞춘 것이다. 만약 저장소 구조가 크게 바뀌었거나 사용자가 특정 영역만 봐달라고 하면 이 분류를 그대로 따르지 말고 상황에 맞게 조정한다.

### 4. 종합

네 에이전트 결과를 모아서 실제로 근거 있는 불일치만 추린다. 확신이 안 서는 건(예: 의도적으로 문서화 안 한 내부/테스트 전용 엔드포인트, 서술 층위가 달라서 자연스럽게 겹치는 요약-상세 관계) 억지로 문제 삼지 않는다 — 이 프로젝트는 "합리적인 근거가 있을 때만" 고치는 걸 원칙으로 한다.

### 5. 수정

- 오탈자, 실제 코드와 다른 값, 최근 추가/변경됐지만 문서에 반영 안 된 내용, 문서 간에 서로 모순되는 서술은 바로 문서를 고친다.
- 문서 구조를 새로 만들거나(새 파일 분리 등) 여러 파일에 걸친 큰 재구성이 필요해 보이면, 먼저 사용자에게 확인한다.

### 6. 요약 보고

무엇을 조사했고, 무엇을 발견했고, 무엇을 고쳤는지 한국어로 간결하게 정리해서 사용자에게 보고한다. 발견됐지만 안 고친 것(판단 보류)이 있다면 이유와 함께 명시한다.
